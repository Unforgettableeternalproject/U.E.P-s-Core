## 0. 結論（先看這段）

1. **不拆回模組。** ES 管線整條是 Core Host 託管的單一元件 `EchoPipelineHost`（建議放新套件 `uep/echo/`）。Core 不認識 STT、LLM、TTS 三個獨立模組，只認識「一條會產生 utterance、接受 turn 派工、回報交付證據的管線」。依賴方向固定為 `uep -> echo_stream`；`echo_stream` 永遠不 import `uep`（DECISIONS D3 驗證條件原文）。
2. **這個元件在 Core 眼中同時扮演三個既有契約角色**：輸入提交者（把 utterance 經 Gateway 變成 `input.utterance_final`）、回合執行者（接受 Core 的 TurnTicket 跑 think→speak→sink）、播放端點（CC-4 Lease 持有者與 CC-5 OutputAdapter，對 sink 做第二次接納）。
3. **對 MIN 提出的 TurnExecutor：採用，但修改三處（見 §1.4）。** 回合執行機制（排隊、regen、barge-in 機制、spoken 推算、commit）收進 ES 的 `TurnExecutor`；所有「該不該回、誰先、讓不讓位、PASS」的政策拆成兩層：熱路徑本地規則（ES 內以 Core 預先推送的政策快照執行）、回合級決策（Core 的決策插槽）。執行權一律來自 Core 簽發的 TurnTicket，TurnExecutor 不得自行開 turn。
4. **決策插槽位置**：在 Core 的 Turn Orchestrator 內，介於「utterance 進來」與「簽發 TurnTicket」之間；介面是 `TurnCandidate -> Proposal`，proposer 身分 `core.decision`，只開 Interaction 軸，由 CC-7 裁決，不碰 Risky 核准與 Policy。Laya／Jev 之後只替換這個 proposer 實作，並可先以 shadow mode 並行評估。
5. **記憶**：Core Host 擁有唯一的 engine registry（namespace -> MemoryEngine），以注入、再 `start_dream_scheduler()`、關閉時 stop 的宿主契約運作；ES 現有的 `EchoMemoryAdapter` 接受注入 engine，所以沿用而非重寫，外面再包一層 Core 的 audience／ACL 過濾（Memory Access Layer）。bot 的自帶做夢排程退場有可驗證條件，並與「bot 是否仍自開 engine」綁在一起（§3.4）。
6. **艾斯維爾裁示 #221：所有平台底層一律用「合入 Core 的 ES」，bot 不得保留自己的 turn 執行循環。** 因此 T-07b「ES 輸出端收斂」是本案的**前置切片 S0**（先於 S1，在 ES repo 進行）：它把 TurnExecutor 與可注入策略介面做出來，該策略介面就是 Core 決策層的插槽（§1.4、§4.4）。
7. **七個 PR 切片**（S0 為前置，S1 之後依 §5 平行），S0 -> S1 -> {S2 ∥ S3} -> {S4 ∥ S5} -> S6。
8. **需要艾斯維爾裁決 14 項（D70～D83）**，其中最重要的是 D72（上下文由誰組）與 D73（Output 接納粒度與延遲預算）。

### 1.4 對「TurnExecutor」提案的表態：採用，並修改三處

背景（ES 清單結論 1、3）：bot 沒有用 `PipelineRunner`，而是在 `executor.py` 與 `voice_output.py` 重寫了一套回合循環（排隊、聆聽讓位、regen、PASS）；ES 完全不知道 passive 與讓位；只有 Web 路徑走 `PipelineRunner.run_turn`。Core 若只照 Web 的方式組裝，會漏掉 Discord 多人語意；若照 bot 的方式組裝，等於把第二份編排帶進 Core，違反「禁止重複編排」（提案 §6.2、CC §7.2）。

**採用的部分**：ES 提供單一 `TurnExecutor`，涵蓋排隊、regen、barge-in 機制、spoken 推算、commit、sink 管理，取代 `PipelineRunner.run_turn` 與 bot 自寫循環。這讓 ES 清單 §7 的 a、b、c、h、i 項各收斂為一份實作。

**修改一：執行權來自 Core 的 TurnTicket。** TurnExecutor 不得自行開 turn。每一輪必須持有 Core 簽發的 `TurnTicket`（欄位見 §1.5）；沒有 ticket 的 utterance 只能進決策層，不會被 think。理由：INV-03、V09（單輸入單輸出），以及 bot 現在另建 turn_id 再手動接 `MARK_STT_END` 的做法在 Core 下沒有存身處。regen 的語意固定為「同一 turn_id、**不增加 turn_generation**、新 attempt」：`attempt_id` 由 ES 遞增並寫入 `TurnOutcome.attempts` 回報，Core 收到後發 `turn.attempt_started` 並記錄（T-07b Q10：Core 預發 attempt_id 會讓 regen 也多一次往返，違反低延遲）。因 ES Think 本來就以 turn_id 去重記憶注入，regen 沿用同 turn_id 正好相容；regen 只在尚未出聲時發生，ES 強制 `audio_started` 後不 regen。只有被 barge-in、被取代、被讓位取消才 `turn_generation` +1。

**修改二：政策與機制分層，熱路徑不呼叫 Core。** 讓位、PASS、reply_mode、barge-in 許可這些「政策」不放進 TurnExecutor（排隊固定 FIFO，不開放政策，見 §4.5 Q9）：
- 熱路徑規則（每個音訊 chunk 判斷，例如「passive 模式不做 barge-in」「這位說話者在 barge_user_ids 內」「聆聽者有聲秒數超過門檻就讓位」）由 ES 以 `TurnHostPolicy` 的**本地快照**執行。快照由 Core 在 ticket 簽發時與參與者變動時推送；ES 只讀本地記憶體，`on_voice_event` 在 loop 執行緒上必須快（ES 清單 §4），不能碰 DB。
- 回合級決策（這句話是不是對她說、回不回、走哪條路由、用哪個 reply_mode）由 Core 的決策插槽產生，並寫入 ticket 與政策快照。
理由：bot 現在的 `echo_decision`（aggregator、gate、engagement、authority）本質是決策層，#153 已定位為決策層；而「讓位」的音訊秒數累積又必須在毫秒級本地完成。把兩者硬塞進同一處，不是延遲爆掉就是決策不可替換。

**修改三：取消的權威分兩步。** ES 可立即本地 `sink.stop()` 並取消自己的 token（既有行為），但「這個 turn 已取消」的權威事實由 Core 記錄：ES 回報後，Orchestrator 發 `turn.cancelled`（`reason_code` 分類）、`turn_generation` +1，必要時發 `control.abort`（取消 ES 以外的上游，例如 Part S 的 Task）。ES 不自行發 `control.*`（CC-5 §5.4：任何元件不得自行 revoke／控制）。讓位於「尚未開播」：取消並標 `reason_code=yielded`，不 commit；已開播：交給 barge-in 路徑。

**#221 的落地規則（MIN 補充）。** (1) bot 不得保留自己的 turn 執行循環；`executor.py _run_locked` 與 `voice_output.py VoiceTurn` 的循環在 T-07b 之後只剩「提供策略實作」的薄層，最終由 Core 決策層取代（階段 Y）。(2) T-07b 的產出分兩件：ES 的 `TurnExecutor`（機制），以及注入式策略介面 `TurnHostPolicy`（讓位、passive、PASS、barge-in 許可、排隊優先、regen 觸發）。(3) 本文把 `TurnHostPolicy` 的**回合級部分**直接定義為 Core 決策插槽的下游：決策插槽產生 Proposal，Orchestrator 把它編成 ticket 與政策快照，經 `TurnHostPolicy` 注入 ES；T-07b 期間 bot 提供過渡實作，Core 就位後換成快照驅動的實作，ES 程式不變。(4) 這兩者必須是同一個介面，否則會留下第二條注入路徑。介面形狀以 ES 的 T-07b 介面草案（§17）為準，見 §4.4。

**其他由此帶出的 ES 側要求**（併入 S3 的 ES 前置 PR）：`interrupt` 非 thread-safe，轉接層一律以 `call_soon_threadsafe` 呼叫；ES 清單指出的 `interruption_backoff_s` 只寫不讀（pipeline.py:104），backoff 實際無效，須先修；`LLMThinkStage.active_scope` 為實例屬性，同一個 stage 同時只能跑一條 stream，與「單一 Presence、單一 Interaction 軸」一致，但須在文件明寫為不變條件；Think 的 `history` 為單一 list，不依 speaker／session 隔離，與 audience 規則的關係見 D72。

### 1.5 介面清單

**(a) 事件進出**

| 方向 | 內容 | 通道與規則 |
|---|---|---|
| ES→Core | `input.utterance_final`（interaction） | 由轉接層經 Gateway 提交；`source=core.echo_host`；`idempotency_key=es:<session_ref>:<utterance_seq>`（E-20 字元集）；轉錄文字與 `Utterance.metadata` 的私人部分走 `payload_ref`，payload 只放 ID、語言、信心、毫秒統計、`speaker_ref`（平台字串，如 `discord:<user_id>`）。`actor_id` 由 Gateway 依 Adapter 認證與 Core 身分映射重建，**不取自 payload**（INV-04；未驗證平台身分不得填成 owner，見 D77） |
| Core→ES | `TurnTicket`（程序內呼叫，非事件） | 欄位：`turn_id`、`turn_generation`、`source_turn_ref`（輸入端 id，見 §4.5 Q1）、`conversation_id`、`segment_id`、`audience_scope`、`reply_mode`、授權六元組、`valid_until`、`context_ref?`（視 D72）、政策快照版本。ticket 也落一筆 `turn.started`（durable） |
| ES→Core | 生命週期事實 | `turn.attempt_started`（regen；由 ES 的 `TurnOutcome.attempts` 回報觸發）、`turn.generation_completed`、`turn.cancelled`（`reason_code`）、`delivery.reported`（逐句證據）、`conversation.participant_joined`／`participant_left`、`core.component_health_changed`（stt／tts／think／memory） |
| Core 內部 | `turn.started`、`turn.completed`、`turn.skipped`、`state.*`、`output.*`、`control.*` | 由 Orchestrator／Gate／State Coordinator 發，ES 無寫入權 |

**(b) Output Gate／Presence 控制**

- 轉接層以「端點」身分向 PresenceManager acquire／renew，沿用 `EndpointService` 與 P-21／P-22（in-process 或 loopback，不跨機器）。`endpoint_id` 取 CC-4 §4.1 粒度（Discord：`guild_id+channel_id+interaction_scope`；Desktop：`device_id+client_instance_id`）。
- ES Sink 的第二次接納（P-14）由注入的 `SinkAdmission` 完成：每句播放前與每個 chunk 前檢查六元組、本地剩餘 TTL、`stopped_turn`；結果碼與 Gate 同源（`GateDecision`），實作沿用 `CliEndpoint._admit`（`uep/endpoint/endpoint.py:576`）的規則。ES 只認這個 Port，不認識 uep 型別。
- Presence 非 ACTIVE 時（NONE、RECOVERING、撤銷），轉接層在 `feed` 之前丟棄音訊（P-9：缺席預設不收集原始音訊，V18），並通知 ES 停止當前輸出。這是熱路徑本地判斷，狀態由 Presence 事件維護的本地旗標提供。
- audience：ES 的 `Sentence` 不帶 audience；OutputIntent 的 `audience_scope` 由 Core 依當前 Presence／頻道決定（CC-5），ticket 帶一份供 ES 標註。

**(c) session／turn 對應**

| ES 概念 | Core 概念 | 規則 |
|---|---|---|
| ES 無 session_id；宿主給 `memory.set_session` 字串 | `conversation_id`／`segment_id`（`conv_`／`seg_`） | 轉接層把 `segment_id` 衍生成 ES 的 session 字串（只用於記憶 episode 標記與 exclude 自我回聲）；注意 `set_session` 會重建 ToolExecutor（ES 清單 §6） |
| `Utterance.turn_id`（`new_turn_id()`，uuid 前 12 碼，輸入端 id） | `turn_<ULID>`（TurnTicket 簽發） | turn_id 由 Core 簽發在 TurnTicket；輸入端 id 由 ticket 的 `source_turn_ref` 對應並存 `legacy_ref`，不當主鍵；提交 `TurnRequest` 前轉接層把 `Utterance.turn_id` 覆寫為 ticket 的 turn_id（T-07b 草案要求兩者相等，否則 submit 拒絕）。Web／CLI 無 Core，用 `StandaloneTicketIssuer`（`require_ticket=False`）（CC-1 E-20、§0.3） |

|---|---|---|---|
| BARGE_IN | `barge_in` | 是 | 歷史只記已交付範圍（O-3） |
| SUPERSEDED（同人再呼叫） | `superseded` | 是 | |

| UPSTREAM_ERROR | `upstream_error` | 是 | 對應 CC-3 `error.code`，依 R-4 決定 fallback（新 attempt） |
| SHUTDOWN | `shutdown` | 否 | 對應 `core.stopping`，不終止 Task（E-10、T-11） |
| （Core 發）全域停止／revoke | `global_stop`／`presence_lost` | 是 | `control.stop`／`control.revoke` 經獨立控制通道，直達轉接層，轉接層同步呼叫 ES 的本地停止 |

控制訊號不得排在 journal 或 Bus 後面（CC-5 §5.3）；轉接層的控制 handler 只設旗標並以 `call_soon_threadsafe` 通知 ES，冪等、可並行。

**(e) 執行緒與非同步邊界**

- ES 為 asyncio；`uep/` 為同步 SQLAlchemy 加執行緒。轉接層持有一條專屬 event loop 執行緒跑 ES；ES 對 Core 的任何呼叫（提交事件、取 ticket、回報證據）一律離開 loop（executor），**ES 的 loop 上不得執行阻塞 DB 呼叫**。Core 對 ES 的呼叫一律 `call_soon_threadsafe`。
- CC-3 的 `Runtime.stream` 目前是同步 `Iterator`（`uep/adapters/runtime.py`），與 ES 的 `AsyncIterator` 不同（T-12 已預告橋接）。P3 的處理見 §2 CC-3。

**(f) ES 側缺口（來自 ES 清單 §8，列入 S3 的 ES 前置 PR）**

| 缺口 | 補法 |
|---|---|
| Memory 型別是 `Any` | 定義 `MemoryPort` Protocol |
| ThinkStage 契約缺 `prewarm`／`seed_pending`／`history`／`tools`／`profile`，目前靠 getattr 探測 | 補入契約，移除 `inspect.signature` 探測 |
| MultiChannelInputStage 缺 `on_voice_event`／`on_partial`，`on_partial` 簽名兩邊不同 | 統一為 `(speaker_id, text, index)` |
| AudioSink 缺 `is_active`／`first_frame_at`／`confirm_stopped`；缺逐句播放範圍回報 | 補入契約；新增「每句播放範圍」讀取，供 CC-5 `played_range` |
| 缺 session／channel／guild 欄位 | 以 ticket 欄位承載，不改 `Utterance` 核心欄位 |
| Think／Memory 多數參數只讀 env | 補建構參數覆寫，讓 Core 集中設定（Speak 已有） |
| `DreamScheduler` 只支援單 scope、無 Protocol | 見 §3.3；P3 不再由 ES 啟動 |

### 1.6 ADR

#### P3-ADR-1：ES 以單一 Pipeline 宿主元件接入，不拆模組
- 背景：艾斯維爾要求不再沿用 STT／NLP／MEM／LLM／TTS 分模組策略。
- 決策：`EchoPipelineHost` 託管整條 ES 管線；Core 與 ES 之間只有 §1.5 的窄介面。
- 奈也觀點：這讓 Core 不必再理解「某模組完成了某層」；ES 內部想換 TTS 或 STT 完全不影響 Core。
- 奈留觀點：代價是 ES 內部的健康、延遲、失敗必須用 `core.component_health_changed` 與 telemetry 往外攤開，否則 Core 看不見黑盒內的問題；而且 ES 與 Core 的 Python 版本、事件迴圈模型不同，轉接層是長期維護面。
- 替代方案：把 STT／Think／Speak 各自包成 Core Adapter（等於舊模組制）。拒絕：重複編排，且會破壞 ES 的 stage 重疊延遲設計。
- 後果：Part S 的工具呼叫、Proactive 對 ES 只能透過 ticket 與 Port 介入。

#### P3-ADR-2：TurnExecutor 收進 ES，執行權由 Core TurnTicket 授予，政策分層
- 見 §1.4。奈也觀點：Discord 多人語意不必在 Core 再寫第三套。奈留觀點：只要 ES 能不經 ticket 自行開 turn，單一 turn 擁有者就會退化；且熱路徑快照與 Core 權威狀態之間有時差，必須以 ticket 的 `valid_until` 與政策快照版本號收斂，殘餘風險記在 §6。

#### P3-ADR-3：Memory 由 Core Host 擁有 engine，沿用 ES 的 adapter 邏輯
- 見 §3。奈也觀點：salience 評估、evidence 準備、隱私意圖掃描這些邏輯已經寫好且有測試，不重寫。奈留觀點：這使 Core 依賴 ES 的 `EchoMemoryAdapter` 實作細節，須以契約測試固定其對外形狀，且 ES 清單 §7 d 項（記憶 store 時機兩邊各一套）要先收斂。

#### P3-ADR-4：決策層以 proposer 插槽接入 CC-7，不另開寫入路徑
- 見 §4。

說明：echo_memory 原註解明寫「不併入 memory.consolidated」，故 `memory.consolidated`（對映 legacy `SNAPSHOT_CONSOLIDATED`）與 `memory.record_created` 保持原義，記憶側七種各自獨立註冊。`memory.record_created` 由 MemoryHost 在 ES 的 store 成功後發（只帶 ID）。

**scope_ref 轉譯（#82 與 uep 信封的差異，不改 echo_memory）。** echo 的 `EventDraft` 自帶 `scope_ref`、`idempotency_key`；uep 的 `EventDraft` 沒有 `scope_ref`，scope 在 `TrustedContext`。MemoryHost 的 sink 轉譯器負責：`scope_ref` -> `TrustedContext.scope_ref`；`source=core.memory`、`actor_id=uep:memory`、`external=True`；`idempotency_key` 原樣沿用（echo 端已是內容雜湊，重放同鍵）；`expires_at` 從 payload 搬到信封欄。轉譯器是 fire-and-forget 對 echo 端（echo 的 emitter 在 daemon 執行緒呼叫 `sink.emit`、不讀回傳值），Core 端發布失敗只記 log 與計數，不回拋。

**CC-2。** 現行 §2.2 禁止 ES 自行拼上下文，但 ES Think 自己 retrieve 並組 prompt，並行檢索還是它的延遲最佳化（ThinkStage docstring：retrieve 與 LLM prefill 平行、首句用固定墊句）。這是本案最大衝突，兩種解法見 D72；D72 已裁決（2026-10-30，採 (a)）：P3 規則為 `history_owner = sdk_store`（ES 的 SessionControl 為單一歷史擁有者），Core 端不另寫歷史注入，只從 `delivery.reported` 與 `turn.*` 事件投影 `history_entries` 供稽核與跨 audience 過濾。這樣仍滿足 X-3「單一擁有者」。

**CC-3。** 不強迫 ES Think 實作 `Runtime` Protocol：P3 的一般對話走 `mode=direct_chat`，其推理迴圈在 ES 內，轉接層只對外報告 attempt 與結果。理由是 Runtime 同步介面與 ES 非同步串流之間硬橋接，會在熱路徑加一層執行緒跳轉。待 Part S 的 S3（LLM tool call -> ActionIntent）落地、需要 tool_intent 時，再決定是把 ES Think 包成 Runtime（補非同步變體）或讓 ES Think 以 Port 提交 tool_intent。此處只標「CC-3 §3.1 預留非同步變體」，不在 P3 實作。R-2（取消後晚到結果丟棄）由 TurnExecutor 以 `turn_generation` 與 ticket 失效實現。

**CC-5。** 這是實作上最大的契約缺口：
1. 現行 `OutputAdapter.send` 同步阻塞到播放結束才回 `SendResult`（`CliEndpoint._play` 即如此）。ES 的句子流需要「送入即返回、之後回報播放進度」，否則每句的 `DeliveryManager.dispatch`（prepare、enqueued、claim、apply 至少四個交易，加兩次 Gate 檢查）串在句與句之間，會產生可聽見的空檔。新增 O-16：`send` 允許在 `enqueued`／`sent` 時返回，後續證據由 Adapter 呼叫新增的 `DeliveryManager.report_evidence(delivery_id, evidence, played_range)` 推進，仍受 O-1／O-2／O-12 單向推進與證據只升不降約束。目前 `uep/output/manager.py` 無此入口。
2. 粒度：一句一個 OutputIntent（`sequence=Sentence.index`），`output_id` 以 `(turn_id, attempt_id)`。成本與備案見 D73。
3. 墊片音（gap filler、tool filler）：ES 以保留的 `GAP_SENTENCE_INDEX` 標記。慣例：`origin=persona`、`kind=audio_stream`，`sequence` 使用獨立序列區段，並標 `is_filler`（放 `content_format`），歷史中不計入 `spoken_text`。
4. `played_range` 的來源：ES 的 `AudioSink.played_duration_s` 配合句界對映成逐句範圍（需 §1.5 (f) 的 Sink 擴充）。Discord 只有 `transport_sent`，依 O-2 停在 `sent`，歷史標「已送出，聽眾播放未知」（VC-5-2）。
5. `spoken_text` 粒度 ES 與 bot 現況不同（ES 把部分播出的句子算作已播；bot 整句播完才算），見 D74。

**CC-4。** 沿用。P3 只實作 [A] 首次 acquire 與 [C] 恢復，不碰 [B] 位置移轉（P5）。補一句 P-9 的實作位置（feed 之前丟棄）。ES 作為端點時，P-25（凍結／睡眠殘餘風險）與 P-21／P-22（不離開 loopback）同樣適用，Part H 前不得跨機器。

**CC-6。** P3 不新增條文。注意兩個既有偏離：(1) ES Think 內建 `deep_recall`／`force_remember` 記憶工具，不經 Tool Gateway，屬已知過渡偏離（D79）；(2) 一般對話回合是否建立回合 Task 依 D62 由 Part S 決定，P3 的 ES 回合不建 Task，也不影響 T-1。

**CC-7。** Interaction 軸只有 State Coordinator 能寫（S-1）。轉接層與 ES 只送事實，不是 proposer。Orchestrator 依事件向 CC-7 提 phase 轉換（proposer `core.turn`）；決策插槽另以 `core.decision` 提 reply_mode 相關轉換（例如進入 passive 觀察）。兩者都只在 Interaction 軸。ES 的 `MISCHIEF` 之類 Behavior 值與本案無關，S-5 不動。

### 3.2 現況：三套做夢排程並存

| 排程 | 位置 | 特性 |
|---|---|---|
| echo_memory 內建（APScheduler） | `engine.start_dream_scheduler()` | 閒置與 cron 觸發；ES 認為「lazy、無差別」，所以 `build_engine` 預設關閉 |
| ES `DreamScheduler` | `echo_stream/core/dream_scheduler.py` | 累積優先（pending 達門檻）再閒置；單 scope |
| bot | `echo_memory_service._start_dream_scheduler`（已註明過渡）加 hub 層聚合迴圈 | 呼叫 engine 內建排程；舊版 engine 退回 bot 自有迴圈 |

#129 的宿主契約指定 `start_dream_scheduler()`。但 ES 的設計意圖（2026-08-22）是「做夢不是無預警與無差別，每次都要期待能萃取出 concept」，與內建 idle／cron 的觸發邏輯不同。Core Host 只能留一個擁有者，見 D75。本文建議：把累積門檻做進 echo_memory 內建排程（記憶端改動，因為它才握有 pending 計數與 `MIN_SALIENCE_THRESHOLD`），Host 只負責啟停，ES 與 bot 的排程隨之退場。

### 3.3 ES 側的退場

P3 起 ES 作為 Core 內的函式庫時不再建立 `DreamScheduler`，也不再讀 `ECHO_STREAM_DREAM_*`；該類別保留給 ES 獨立執行（Web）模式。ES 清單 §7 f 項（多 scope 排程）因此不需要在 ES 補做。

### 3.4 bot 自帶做夢排程的退場條件

關鍵事實：bot 的 `EchoMemoryService` 為每位使用者各開一個 engine，且 echo_memory 不是 thread-safe、也非多行程共用 engine 的設計。若 Core MemoryHost 與 bot 對同一資料目錄各開 engine，`FileLease` 只擋得住做夢互斥，擋不住 retrieve／store 併發。所以退場分兩階段：

**階段 X：並存（P3 內）。** MemoryHost 只管 Core 自己的 ES 使用的 namespace 與資料目錄；與 bot 的 per-user 目錄**必須不相交**（目錄與 namespace 清單於 S2 驗收前核對）。bot 維持現狀，包含過渡排程。

**階段 Y：退場（晚於 P3，P4 Discord Adapter 正式化時）。** 全部成立才可移除 bot 的做夢路徑：

| # | 條件 | 如何驗證 |
|---|---|---|
| E1 | Host 做夢排程已啟動，或因他行程持租約而 skipped（兩者皆正常） | MemoryHost 啟動 log 與狀態；租約持有者行程 ID |
| E2 | bot 不再自建 engine，記憶讀寫改走 Host 的 MemoryPort；且依 #221 bot 已無自有 turn 執行循環（T-07b 完成） | bot 端 `EchoMemoryService` 的 engine 建構點為 0；以 import／呼叫掃描驗證 |
| E3 | bot 的 `_start_dream_scheduler` 以設定關閉，hub 聚合迴圈關閉 | 設定旗標與單元測試 |
| E4 | 觀察期（建議 7 天，D76 確認）內：bot 觸發的 dream 次數為 0；租約衝突為 0；每個 pending ≥ 門檻的 namespace 至少被 Host 蒸餾一次 | Host 計數器：`memory.dream.skipped_lease`、`memory.dream.runs{trigger}`、bot 端觸發計數 |
| E5 | 回滾路徑：旗標切回即可恢復 bot 自帶迴圈，且不遺失資料 | 演練一次 |

## 4. 決策層插槽

### 4.1 位置

在 Turn Orchestrator 內，順序：

```
Utterance 流 ─► TurnAggregator（多人轉錄窗、turn 聚合）─► TurnCandidate
            ─► TurnProposer（可替換）─► Proposal
            ─► Orchestrator 驗證 ─► CC-7（core.decision 提請求，裁決）
            ─► 簽發 TurnTicket（或寫 turn.skipped）
```

`TurnAggregator` 與 `TurnProposer` 是兩個可獨立替換的 Port（#153 把「多人轉錄窗與 Turn 聚合」與「回不回」都歸決策層；Laya／Jev 可能只換後者）。預設實作由 bot 現有 `echo_decision` 的 aggregator、gate（wake_detector、context_tracker）、engagement 邏輯搬入；ES 的 `AddressingClassifier` 目前沒有宿主使用，合併進預設 proposer。

### 4.2 介面（只列契約，不選模型）

`TurnCandidate`（輸入）

| 欄位 | 說明 |
|---|---|
| `candidate_id` | 冪等 |
| `utterance_refs` | 一或多個 utterance 的事件 ID（文字以 ref 取，proposer 在 audience 內讀取） |
| `speakers` | `speaker_ref` 清單與角色（authority 解析結果） |
| `conversation_id`／`segment_id`／`audience_scope` | 範圍 |
| `interaction_state` | 當前 Interaction 軸與版本（`expected_version` 來源） |
| `presence` | 是否 ACTIVE、endpoint |
| `recent_turns` | 最近 turn 的 ID 與交付摘要（不含未交付內容冒充已說） |
| `deadline` | proposer 必須在此前回覆 |

`Proposal`（輸出，僅為提議）

| 欄位 | 說明 |
|---|---|
| `addressed` | 是否對她說，附 `confidence` |
| `reply_mode` | `respond`／`passive`／`pass`／`defer` |
| `route` | `direct_chat`／`agent_loop`／`task_request`／`ignore`；後兩者只是建議，實際建立 Task 仍走 Task Manager 與 Policy（D62） |
| `interaction_to` | 建議的 Interaction 軸目標狀態 |
| `yield_hint` | 供政策快照使用。`queue_priority` 不放（ES 排隊固定 FIFO，見 §4.5 Q9） |
| `reason_code`、`proposer_id`、`proposer_version` | 稽核；原因碼限安全字元集，不含原文 |

### 4.3 規則

- proposer 身分 `core.decision`，只加入 `DEFAULT_PROPOSERS[Interaction]`，不開 Behavior 軸（比照 D63，S-5）。
- Proposal 是提議：Orchestrator 先驗證（列舉值、`expected_version`），再以 `state.transition_requested` 送 CC-7；被拒（`REJECTED_VERSION`／`REJECTED_ILLEGAL` 等）則以預設行為回退，不重試風暴。
- Core 保留否決權且 proposer 不可繞過：Presence 非 ACTIVE、全域停止成立、audience 不允許時，`reply_mode` 一律強制為 `pass`；Proposal 對 Risky 核准（T-4、T-5）與 Policy 沒有任何作用，輸出也不能自稱已核准。
- 逾時或例外：回預設 Proposal（被點名或單人 -> `respond`；多人未被點名 -> `passive`），並發 telemetry。預算（毫秒）待 D80。
- 輸入含私人轉錄：proposer 讀取受 audience 與 `data_egress` 約束；若實作為外部模型，無符合出口則明確失敗回預設，不擅自改送其他供應商（R-6 精神）。模型輸出一律視為不受信資料，只接受 schema 內的列舉。
- Shadow mode：新 proposer（Laya／Jev 評估品）可與預設 proposer 並行執行，只記錄差異（`turn.skipped` 之外的 telemetry，不寫 `state.transition_requested`），用於選型證據；與 P7 的 shadow 概念一致。
- 替換方式：以 `proposer_id` 註冊，設定選用；Orchestrator 不依賴任何具體實作。

### 4.4 策略注入合約（#221，與 T-07b 對齊）

**注入鏈。**

```
TurnProposer（可替換；Laya 掛這裡）
   └► Proposal ─► Orchestrator 驗證 ─► CC-7 裁決（core.decision，Interaction 軸）
                                          └► 通過後 Orchestrator 編譯成
                                             TurnTicket + PolicySnapshot(version)
                                                └► 經策略插槽（BargeInPolicy／YieldPolicy／
                                                   SpeechTextFilter／ModeRules／RegenPolicy）
                                                   注入 ES TurnCoordinator
```

**兩層分工。**

| 層 | 呼叫頻率 | 誰實作 | 能做什麼 | 不能做什麼 |
|---|---|---|---|---|
| 回合級決策（`TurnProposer`） | 每個 TurnCandidate 一次，有 deadline | 預設規則實作；之後 Laya／Jev | 提議 reply_mode、route、yield_hint、queue_priority、interaction_to | 直接寫任何狀態軸；批准 Risky；改 Presence；繞過 Gate |
| 熱路徑策略（ES 策略插槽，統稱 `TurnHostPolicy`） | 每個音訊 chunk、每次 regen 判斷 | ES 內的規則執行器，**只讀 Core 推送的 PolicySnapshot** | 依快照判斷是否讓位、是否允許某說話者 barge-in、passive 下不播、生成中 PASS 丟棄、regen 次數上限 | 同步呼叫 Core、DB、或任何模型 |

**合約要點（建議 T-07b 的介面草案以此為準，ES 正在出草案，到時對照修正）。**
1. **方法集以 T-07b 草案 §17 為準**（取代本文先前的建議稿）。全部同步、純計算、不得 I/O（每個 VAD chunk 約 20–100ms 在 STT 執行緒呼叫）：

| 策略（草案名稱） | 輸入 -> 輸出 | 說明 |
|---|---|---|
| `BargeInPolicy.on_voiced(turn, ev)` | `TurnView`（含 `reply_mode`、`barge_users`、`sink_active`）、`VoiceEvent` -> `InterruptionDecision` | ES 提供預設的累積式實作（有聲秒數累積、gap 重置 0.5s、`is_active` 才武裝、成立後連帶取消排在後面的輪次）；門檻由快照的平台 preset 給 |
| `YieldPolicy.on_voiced(ev, live)` | `VoiceEvent`、live turns -> `list[YieldAction(turn_id, reason)]` | 單一事件不足以判斷（需累積秒數與 live turn 狀態），累積器由 ES 提供、讀快照門檻；預設 `NeverYield`；結果經 `call_soon_threadsafe` 套用，`reason` 以 `SUPERSEDED` 加 detail `yielded` 表示 |
| `ModeRules` | `reply_mode`（不透明字串）-> `speak`、`barge_in` 兩個旗標 | 建立 turn 時評估一次；`reply_mode` 本身由 Proposal 決定並寫入 ticket，ES 不「計算」它 |
| `SpeechTextFilter.feed(sentence)` | 句子文字 -> 字串或 None；`passed` 屬性 | 句級標記剝除與生成中 PASS 偵測（內容級，不可能是 ticket 級）；Discord 的 `@名字:` 標記協定留在 bot 實作 |
| `RegenPolicy.refresh(turn)` | `TurnView` -> `Utterance` 或 None | 有值 = 丟棄舊回覆重算；`max_regenerate` 與「`audio_started` 後不重算」由 ES 強制，turn_id 沿用 |

與本文先前建議稿的差異：`admit_utterance` 不納入（輸入端已把 utterance 交給宿主，admit 屬 Core 決策層，發生在 Aggregator／Proposer 之前）；`reply_mode_for` 改為 `ticket.reply_mode` 加 `ModeRules`；`barge_in_allowed` 拆為 `ModeRules.barge_in`、快照參與者表（`barge_users`）與 `BargeInPolicy`；`queue_order` 不開放（FIFO）；`on_pass` 分兩種：生成前 PASS = Proposal `reply_mode=pass`、Core 不簽 ticket 並發 `turn.skipped`，生成中 PASS = `SpeechTextFilter.passed` -> `TurnOutcome.skipped_reason="pass"`，Core 依 outcome 記錄；`regen_allowed` 改為 `RegenPolicy.refresh`。另新增 `SinkFactory`、`on_sentence`、`spoken_rule`、`commit_mode`（見 §4.5）。
2. `PolicySnapshot` 帶 `version`、`valid_until`、參與者表（`speaker_ref`、角色、`barge_in` 許可）、`reply_mode`、讓位門檻、`yield_hint`、**平台 preset**（barge-in 累積門檻與 gap 等，見 §4.5 Q4）。ES 在 `TurnOutcome.snapshot_version` 回報用了哪一版。過期或版本落後時，ES 退回最保守預設（不開新輸出、不 barge-in 新對象），不得沿用過期的寬鬆規則。
3. 快照由 Orchestrator 在簽發 ticket 時、參與者變動（`participant_joined`／`left`）時、Presence 或全域停止變化時推送；ES 回報套用的版本，Core 可稽核「某次讓位用的是哪一版快照」。
4. ES 的 TurnCoordinator 沒有預設的 passive／讓位／PASS 行為，沒有策略就是 `NeverYield`、ES 預設累積式 barge-in（0.4s）、無 filter、單人 respond（Web 模式的既有行為），避免出現隱性的第二套政策。快照過期或版本落後時退保守：累積式 barge-in 只對已在 `barge_users` 的說話者生效、`YieldPolicy` 停用、不擴張新輸出。
5. Laya 之後掛的位置只有一個：`TurnProposer`（以及視需要的 `TurnAggregator`）。模型**不進**熱路徑；若日後想讓模型調整讓位門檻，也只能透過輸出 PolicySnapshot 的參數（例如門檻值、`yield_hint`），由 Orchestrator 驗證範圍後下發，仍不逐 chunk 呼叫模型。
6. State Coordinator 的角色：只裁決 Interaction 軸的轉換請求（`core.turn` 的 phase、`core.decision` 的 reply_mode 相關轉換）。它不持有政策，不直接呼叫 ES；ES 看到的一切來自 ticket 與快照。
