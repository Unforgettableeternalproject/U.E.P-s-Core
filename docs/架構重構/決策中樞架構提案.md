## 0. 結論（先看這段）

1. **中樞是一個葉節點套件 `uep/decision/`（建議名），輸出的是「計畫」（`DecisionPlan`），不是標籤。** 各子系統發 `DecisionRequest`，收 `DecisionResult`（內含 outcome＋plan）。中樞不持有任何權威狀態、不直接呼叫別人；套用計畫的是各權威擁有者（Presence Manager、Task Manager、Orchestrator、Provisioner、Output 側）。
2. **硬閘不收編。** Output Gate、State Coordinator 的轉移裁決、Global Stop、Tool Gateway capability 檢查、Task approval、Presence Lease 全部維持原權威。機制是：請求方先算硬事實放進 `constraints`，並由此算出 `allowed_outcomes`；中樞只能在集合內**收窄**選擇，輸出再過驗證。分數無從覆蓋授權。
3. **熱路徑（每個音訊 chunk）不逐事件問中樞。** 中樞對 B 層的決策輸出是「發布 PolicySnapshot（門檻、模式、許可名單）」——就是現有 `HostPolicySource` 的模式，被正名為中樞的一種輸出形式。
4. **決策不是單向的。** 計畫帶 `reeval_on`（重新請求的觸發點）；迴圈中途缺能力時，迴圈只能發「候選事件」描述缺口，由中樞重新決策——與工具層已談定的不變條件一致。
5. **與 Agent 層的接口：** 中樞是 `LoopTrigger` 的上游——決定「要不要觸發、以什麼範圍觸發」；`DecisionPlan.capability`＋`loop` 區段由套用者（Orchestrator／事件入口）組成 `LoopTrigger`；`capability_tags` 只收窄（AL-3）；`resume` 不經中樞；迴圈特殊情況可經 `decision.consult` 把決定委派給中樞當「指示器」，只得建議、不得擴權（§4.6.6）。
6. **遷移先包裝再擴張：** P0 把 `TurnOrchestrator._propose` 包成 `hub.decide("turn.reply")`，行為零變化；之後才收編輸出側、計畫（預載／平台／輸出處置）、主動與 Agent 迴圈、學習模型。
7. **內部英文：** 翻譯只服務「特徵抽取」支路；喚醒詞比對、語言碼選池、人設回覆維持原文。翻譯與聚合視窗重疊，不佔 300ms 決策預算（細節 §5.4）。

## 1. 決策點盤點

## 2. 定位與邊界

### 2.1 系統概覽

```
                       ┌───────────────────────────────────────────────┐
 Orchestrator ────────►│                                               │
 Output 側 ───────────►│        Decision Hub  (uep/decision/)          │──► DecisionResult
 Proactive/排程 ──────►│  registry · guard · engines · shadow · log   │       outcome + DecisionPlan
 Agent 迴圈(候選事件)─►│                                               │
 Memory/Dream ────────►└───────▲───────────────────────────┬───────────┘
 Model/Tool 層 ───────►        │ 唯讀快照(ports)            │ publish
                               │                           ▼
   State · Presence · Policy · Tool registry          PolicySnapshot (B 層熱路徑)
   (權威擁有者；中樞只讀其投影)

  DecisionPlan 的套用者(各自權威，自行取用結果)：
    reply/output ─► Orchestrator／Output 側      provisioning ─► module coordinator
    placement ─► Presence Manager／Task Manager   loop ─► Agent 迴圈(經 Task Manager)
```

依賴方向（單向）：`uep/decision/contracts` 是葉節點（純型別，只依賴標準庫與 pydantic）；各子系統 import contracts；`uep/decision/` 本體只透過注入的 **ports** 讀快照，**不 import** `presence`、`tasks`、`state`、`turn`。`uep/turn/` 現有的決策實作（`RuleProposer`、`EngagementMonitor`）搬入或註冊為中樞的 engine。需配合 `tests/uep/test_import_boundary.py`（新增規則：`uep/decision/` 不得 import 其他 `uep/*` 業務套件；`uep/` 其他套件可 import `uep.decision.contracts` 與 client）。

### 2.2 與相鄰元件的權責

| 元件 | 權威擁有 | 中樞可做 | 中樞不可做 |
|---|---|---|---|
| Presence Manager／Output Gate | Lease、epoch、輸出放行 | 提議「要不要產生 intent、什麼 kind／style」「要不要請求移轉」；讀 Presence 投影作 constraints | 決定 admit；核發 Lease；繞過 Gate |
| State Coordinator（CC-7） | 軸狀態轉移 | 在 plan 中帶 `interaction_to` 建議 | 自己提 CC-7 請求（由呼叫方 Orchestrator 以 `core.decision` 提，維持現狀） |
| Policy／Approval／Global Stop | 授權、Risky 核准、停止 | 讀結果作 constraints | 覆蓋；自稱已核准；放寬 |
| 工具層（Tool registry／Tool Gateway） | 工具註冊、capability 投影、副作用 | 提 `capability` 收窄範圍（`capability_hint`，只能收窄，公式見 §4.6.2）、提 provisioning 步驟 | 新增 capability；執行工具 |
| Agent 迴圈 | 迴圈內每一步 | 決定**要不要啟動、以什麼範圍啟動**、何時重新評估；被迴圈以 `decision.consult` 諮詢時給建議（§4.6.6） | 決定迴圈內步驟（consult 只是建議，由迴圈採用）；迴圈執行中擴大 capability_set |
| Proactive Engine | 觀察→候選的資料與去重 | 本身就是中樞的一組決策點（`proactive.*` kind）；候選資料結構由 Proactive 擁有 | 把高分當成授權 |
| Memory／Dream | 記憶與做夢執行 | `memory.dream` kind 的排程決策 | 觸發 Patch Gate 等子系統內部判斷 |
| Model Gateway（未實作） | Provider 轉接 | 提模型偏好與必要能力、資料出口要求 | 把私人資料送到不符 `data_egress` 的供應商 |

### 2.3 硬約束的契約機制（不是一句原則）

```
呼叫方(權威側) ──算硬事實──► constraints{presence_active, stop_engaged, audience_scope,
                                         capability_snapshot, approval_state, data_egress…}
              └──據此算出──► allowed_outcomes（例：Presence 非 ACTIVE ⇒ {pass}）
中樞 ─ 只能在 allowed_outcomes 內選；plan 欄位只能「收窄」constraints 允許的範圍 ─►
輸出經 validate（列舉＋安全字元集，沿用 validate_proposal 的作法）─ 不合法 ⇒ fallback
套用者收到 plan 後，仍各自過自己的權威裁決（Gate／CC-7／Policy／Tool Gateway）
```

三道防線：①請求方先縮集合 ②驗證器擋非法值 ③套用者權威再裁一次。模型型 engine 在結構上沒有越權路徑。這與 P3 §4.3「Proposal 對 Risky 核准與 Policy 沒有任何作用」同義，只是從 turn 層推廣到全系統。

> 【奈也】我想這樣的好處是：新增決策點時不用重新討論「它能不能越權」，答案永遠是「不能，因為它拿不到更大的集合」。
> 【奈留】代價是請求方必須負責算對 `constraints`——算錯（漏填）等於授權洞。所以 `constraints` 必須由權威側的**唯一 helper** 產生，而不是各呼叫方手填；列入風險。

## 3. 統一契約草案

型別為示意，不含實作。命名避開既有 `Decision`（`uep.state.coordinator.Decision`）、`GateDecision`、`TurnDecision`、`InterruptionDecision`、`DreamDecision`、`StateDecision`，統一用 `DecisionRequest`／`DecisionResult`／`DecisionPlan`（見待裁決 Q11）。

### 3.1 決策點註冊（類似工具註冊）

// DecisionPointSpec —— 註冊一種 decision_kind
interface DecisionPointSpec {

  mode: "sync" | "async" | "publish";   // 同步請求／非同步請求／發布快照

### 3.3 DecisionResult 與 DecisionPlan

```typescript
interface DecisionResult {
  decision_id: string;
  request_id: string;
  kind: string;
  outcome: string;                      // ∈ allowed_outcomes
  plan?: DecisionPlan;                  // 可空：多數小決策只有 outcome
  confidence: number;
  reason_code: string;                  // 安全字元集，不含原文
  engine: { tier: "rule"|"feature_rule"|"model"|"llm"|"fallback"; id: string; version: string };
  fallback: boolean;                    // 逾時／例外／驗證失敗
  valid_until: string;                  // plan 的有效期；過期須重新請求
  plan_version: number;
  supersedes?: string;                  // 取代哪個舊 decision_id
}

// DecisionPlan：所有區段皆選填，且只能收窄 constraints
interface DecisionPlan {
  route?: "direct_chat" | "agent_loop" | "task_request" | "ignore";
  reply?: {
    mode: "respond" | "passive" | "pass" | "defer";            // 沿用 Proposal 語彙
    delivery: "sync_reply" | "ack_then_report" | "report_only"; // 同步回覆／先暫態再回報／只回報
    interim?: { kind: "transient_ack" | "filler" | "none"; ttl_ms: number };
    interaction_to?: string;                                    // 建議的 Interaction 軸目標
  };
  output?: {
    modalities: ("text"|"audio_stream"|"typing"|"animation")[]; // 對應 OutputKind
    tts: boolean;                                               // 要不要經過 TTS
    emotion: { source: "none" | "llm_marker" | "preset"; preset?: string };
    history: "commit" | "ephemeral";                            // 暫態訊息不進 LLM 歷史(待裁決 Q8)
  };
  capability?: {                                                // 對齊工具層（CapabilityTag 閉集）
    capability_hint?: string[];                                 // 只能收窄；等同 Proposal.capability_hint
  };                                                            // 最終 capability_tags 由 §4.6 公式算出
  provisioning?: Array<{                                        // 預先鋪路徑：模組／工具
    module_id: string;
    action: "keep" | "warm" | "load" | "unload";                // 注意：沒有 "install"(見 ADR-04)
    tool_ids?: string[];
    ready_by_ms?: number;                                       // 需要在何時前就緒
    on_not_ready: "interim_then_wait" | "degrade" | "fail";
  }>;
  placement?: {                                                 // 預先鋪路徑：平台／executor／Presence
    target_platform?: string;
    executor_ref?: string;
    presence_intent: "stay" | "request_move" | "none";
    audience_scope_max?: string;
  };
  model?: { capability_required: string[]; provider_pref?: string[]; data_egress: string };
  loop?: {                                                      // 啟動範圍，不含迴圈內步驟
    start: boolean; trigger_kind?: "user_turn"|"task_request"|"external_event"|"proactive";
    goal_code?: string;                                         // 語意短碼(閉集)，非自由文字
    policy_ref?: string;                                        // 預算與中斷政策由 Policy 解析，plan 不帶數值
    reeval_on: Array<"capability_gap"|"tool_result"|"user_interrupt"|"timeout"|"presence_change">;
    outcome?: "continue" | "finalize";                         // 只用於 consult(loop_end) 的 advice；start 路徑不填
  };
  followups?: Array<{ kind: string; after_ms?: number; on_event?: string }>; // 後續請求(如完成後回報)
}

// 發布型輸出(mode = "publish")
interface PolicyPublication { kind: string; snapshot: PolicySnapshot; version: number; ttl_s: number }
```

規則：
- `plan_sections` 白名單：某 kind 只能填註冊時宣告的區段（例如 `memory.dream` 不得填 `placement`）。
- plan 是**提議的集合**，不是命令；每個區段由對應套用者驗證並執行。
- `loop.outcome` 僅出現在 `loop.consult(loop_end)` 的 `advice`，承載「續想或結束」；`turn.reply`／`plan.refine` 的 `loop` 區段不得填。
- `provisioning.on_not_ready = interim_then_wait`：Orchestrator 先發暫態訊息，迴圈以 `park(await_ready:<tool>)` 等待，受 `warm_wait_budget` 限制；逾時改走 `degrade` 或 `fail`。對齊工具層 §5.8：warming 工具預設不投出給模型，僅以 `capability_set.pending: [{tool, reason:"warming"}]` 供 AgentLoop 讀取，不允許投出後讓呼叫端阻塞等待。`warm_wait_budget` 數值工具層尚未定。
- 所有欄位為英文列舉／ID。使用者可見字串不在 plan 內（邊界處再翻成 zh-TW）。

### 3.4 三種模式與 consult 子型

| 模式 | 呼叫形態 | 例 | 預算 | 逾時 |
|---|---|---|---|---|
| **sync** | `decide(req) -> Result`，呼叫方等待 | `turn.reply`（現 300ms 插槽）、`output.shape` | 註冊時宣告；沿用 `ProposerGuard`（單執行緒、busy 時立即回預設） | `on_timeout` 預設＋ telemetry |
| **sync／consult 子型** | 迴圈經 `decision.consult` 工具呼叫，走 ActionIntent 路徑；中樞內部仍是 `decide()` | `loop.consult`（6 個 sub-kind，見 §4.6.6） | 300ms 快速欄位，不觸發 `plan.refine`；計入迴圈步數 | 逾時回 `advice=∅`＋`reason_code=consult_timeout`，迴圈採用 §4.6.6 的 fail-safe 預設表 |
| **async** | `submit(req)`，結果以事件／回呼到達 | `turn.interject`（tick）、`memory.dream`、`proactive.initiate`、`module.prepare`、`placement.select`、`plan.refine` | 以 deadline／TTL 管，不阻塞熱路徑 | 結果過期即丟棄；候選維持 DEFERRED |
| **publish** | 中樞算出快照並推送，消費者只讀 | `policy.snapshot`（barge-in 門檻、讓位、ModeRules、barge_users）、`channel.mode` | 非請求式 | 快照 `ttl_s` 過期 ⇒ 消費者退保守（現有 Q-5 語意） |

**consult 為何歸入 sync 的子型、不另立第四種模式：** 它與 `turn.reply` 共用同一個 `decide()`、`ProposerGuard` 預算、validate、shadow 與決策日誌；差異只有兩點——呼叫方是 AgentLoop（經工具層註冊的 internal_read 工具），以及 `constraints` 由**當前 Run 凍結範圍**決定而非當輪快照。若將來 consult 需要獨立預算或獨立 engine 鏈，再升為獨立模式。

`DreamLoop.tick`（`dream_loop.py:226`）與 `RuleProposer.tick`（`rule_proposer.py:216`）是 async 模式的兩個現成樣板；`HostPolicySource.publish_channel_mode`（`echo/policy.py:99`）是 publish 模式的現成樣板。

## 4. 預先鋪路徑：DecisionPlan 的設計理由與運作

舊系統是單向的「決策→設定路徑」。新增範疇的核心是：**決策在使用者還沒要求之前就開始鋪路，且鋪路本身會失敗、會過期、會被重新決策。**

### 4.1 四類鋪路對照

| 艾斯維爾的需求 | plan 區段 | 套用者 | 失敗時 |
|---|---|---|---|
| 依意圖預先安裝並啟動需要的模組；不需要時不載入（lazy load／預熱） | `provisioning[]`（keep／warm／load／unload） | module coordinator（中樞只提議；工具註冊表只維護 readiness，見 Q5） | `on_not_ready`：墊暫態訊息等待／降級／失敗；不讓 turn 卡死 |
| 任務要在特定平台執行，直接鋪好路徑 | `placement`（平台／executor／Presence 意圖） | Presence Manager（移轉提議）、Task Manager（executor 綁定） | 移轉被拒（`DENIED`）⇒ 回報中樞重新決策或列待交付 |
| LLM 輸出處置：要不要 TTS、附情緒、暫態還是等結果 | `reply.delivery`＋`reply.interim`＋`output` | Orchestrator／Output 側（決定產生什麼 `OutputIntent`），Gate 仍照常 admit | Gate 拒絕＝照舊：不得自稱已送出 |
| 後續系統層運作套用同一概念 | `followups[]`、`loop.reeval_on` | 各自權威 | 沿用 reeval |

### 4.2 兩階段（保護 300ms 熱路徑）

```
turn.reply (sync,300ms) ──► outcome + route + reply.delivery + 粗粒度 capability_hint
        │                         └─ 立刻簽 ticket，ES 開始 think（沿用現流程）
        └─► plan.refine (async)  ──► provisioning / placement / loop / output 細節
                  │                     └─ 期間以 interim(暫態 ack／墊片) 墊底
                  └─ 完成時發 decision.made(plan_version=2)，套用者取用
```

- 第一階段只回**快速欄位**，不因預載決策拖慢首音。
- 第二階段可用較貴的 engine（特徵＋學習模型、必要時 LLM），結果以 `plan_version` 遞增、`supersedes` 指向第一版。
- 若 `route = direct_chat`，第二階段通常為空（零成本）。

### 4.3 對應 bio_tagger 的初版映射（特徵→計畫）

| BIOS 特徵 | `addressed` | `route` | `reply.delivery` | 預載傾向 |
|---|---|---|---|---|
| CALL | true | `direct_chat` | `sync_reply` | 無 |
| CHAT | 依其他規則 | `direct_chat` | `sync_reply` | 無 |
| DIRECT_WORK | true | `agent_loop` | `ack_then_report`（先暫態再回報） | 依詞彙／領域標籤預熱常用工具集 |
| BACKGROUND_WORK | true | `task_request` | `report_only` | 依任務類別預配置 executor |

### 4.4 迴圈中途重新請求（非單向）

```
迴圈執行中發現缺能力/缺模組 ──► 發「候選事件」(只描述缺口：需要什麼類別能力，不自行擴權)
        │
        ▼
 中樞 loop.reeval (async) ──取 [預設標籤表 ∩ hint ∩ 快照] 及 Policy──► 新 DecisionResult(plan_version+1)
        │                                                      │
        ├─ 允許：provisioning(load) → 工具層註冊表重新投影 capability_set(新版本)
        └─ 不允許：reason_code 回給迴圈，由迴圈自行降級或回報使用者
```

> 註（DL-4）：公式中的「快照 capabilities／政策快照.capabilities」在程式中是 `FrozenMap`（`uep/context/snapshot.py:192`），不是標籤集合；計算時使用的是另行提供的標籤集合（短期取已註冊且 enabled 的標籤，等同不收窄；長期由工具層 `enabled_tags()` 提供）。見 [Capability收窄ADR](Capability收窄ADR.md)。

- **不變條件（已談定，沿用）：** 迴圈執行中不得自行擴大 `capability_set`；要更大能力必須發新候選事件經中樞。本文只補一點：中樞的 re-decision 也受 `reeval_allowed`、次數上限、預算約束，防止「缺能力→重請求」變成迴圈。
- 觸發點由 plan 的 `loop.reeval_on` 宣告；使用者插話、Presence 變動等外部事件也走同一條路。

### 4.5 暫態訊息與等待結果（輸出處置）

#### 4.6.2 capability 收窄公式（兩階段下仍單向）

```
capability_tags = ROUTE_DEFAULT_CAPABILITIES[route]     (中樞維護；詞彙 CapabilityTag 由工具層擁有)
                ∩ (plan.capability.capability_hint  若非空)
                ∩ 政策快照.capabilities
registry.project(capability_tags, ctx) -> capability_set  (工具層；§6.1)
```

- `ROUTE_DEFAULT_CAPABILITIES["agent_loop"]` 含 `decision.consult` 標籤，且 **`capability_hint` 不得收窄掉它**：hint 交集只作用於其餘標籤，`decision.consult` 恆保留（hint 缺該標籤不算收窄，也不計 `decision.hint_dropped`）。理由：依 AL-3，`capability_set` 不含該標籤時迴圈不能呼叫 consult，收窄掉即讓迴圈失去向中樞諮詢的途徑；該標籤副作用上限僅 `internal_read`，保留並不擴權。只有 `政策快照.capabilities` 可移除它（此時迴圈用 §4.6.6 的 fail-safe 預設）。
- 第一階段（`turn.reply`，300ms）即可算出 `capability_tags`，足以啟動迴圈；第二階段（`plan.refine`）**只能進一步收窄或加入 `provisioning`，不得放寬**（plan_version 遞增時的單調規則，與 AL-3 同構）。
- hint 含表外標籤的處置（工具層 §10.2 待填，本文建議）：**表外標籤丟棄並計 `decision.hint_dropped`**，不使整個 Proposal 無效；除 `decision.consult` 外交集為空且 route 為 `agent_loop` ⇒ 降為 `direct_chat`（reason_code `capability_empty`）。見 Q18。
- 中樞**不產生 tools JSON**，plan 內只有標籤；D60（`render_tools` 為唯一產生點）不受影響。
- 標籤的「副作用上限」鎖在註冊表（工具層 RA-6），中樞不需也不能表達副作用等級。

#### 4.6.3 AL-3 與中樞重新決策

| 情境 | 流程 |
|---|---|
| 迴圈內需要更大能力 | 迴圈結束本 Run，並隨結果送出「候選事件」（缺口類別＋`decision_id`，不含擴權結果）；迴圈本身不發 `LoopTrigger`（AL-1）→ 中樞 `loop.reeval` 裁定是否發出新的 `LoopTrigger`（新 Run，`parent_run_id` 連結；由套用者組裝），或拒絕並回 reason_code；若是 consult 中樞自己判斷需要更大範圍，則只回 `escalate`（§4.6.6），流程相同 |
| Run 恢復（核准後、重啟後） | 不經中樞；沿用 checkpoint 凍結集合 ∩ 當下快照 |

> 【奈留】工具層 AL-3 說「產生新的觸發事件並重新經過決策層」，但沒說是同 Run 重凍結還是新 Run。同 Run 重凍結會使「一個 Run 的授權邊界可在 checkpoint 驗證、可重放」失效，故**一律新 Run**——此點隨艾斯維爾裁決 Q-A（採 A）與 `decision.consult` 的「不可擴權、只回 escalate」語意，**已定案**（Q17）。

#### 4.6.6 `decision.consult`：迴圈把決定委派給中樞（艾斯維爾裁決 Q-A 採 A 之補充）

原則不變：中樞決定「要不要啟動、範圍多大」，迴圈只管步驟。特殊情況下迴圈可把某個決定**委派**給中樞，把中樞當作「可呼叫的指示器」。介面與工具層已談定。

| 面向 | 設計 |
|---|---|
| 形式 | 中樞對迴圈曝光一個內部諮詢介面 `decision.consult`；在工具層註冊表（`ToolEntry`）列為 **`internal_read`** 工具，走**同一條 ActionIntent 路徑**（`create_action`→`execute_action`→receipt），因此有軌跡、受 capability 投影約束；工具層負責註冊、投影與執行管線，中樞只提供背後的 executor（呼叫 `decide()`） |
| 呼叫 kind（首版 6 個） | `speak`（要不要開口／插話）、`output_modality`（TTS／情緒／暫態）、`placement`（平台／executor）、`ask_user`（是否先問使用者）、`loop_end`（續想或結束）、`followup`（是否排後續回報） |
| 回傳 | `advice`（對應 kind 的 `DecisionPlan` 片段：`speak`→`reply`；`output_modality`→`output`；`placement`→`placement`；`ask_user`→`reply`（`defer`／問答）；`loop_end`→`loop`（只填 `loop.outcome`）；`followup`→`followups`）、`reason_code`、`confidence`、`escalate`（`{needed: bool, reason_code}`）、`decision_id` |
| 語意 | **只是建議，由迴圈採用或不採用。** 硬閘（Gate、Policy、approval、全域停止）照舊只當 `constraints` 輸入；迴圈採用建議後仍要過各自權威（例如 `output_modality` 建議 TTS，實際輸出仍由 Orchestrator 發 intent 經 Gate） |
| 不可擴權 | `advice` **只能落在當前 Run 凍結的 capability 範圍內**（`constraints.capability_snapshot` = checkpoint 凍結集合 ∩ 當下快照）；`placement`／`output_modality` 的建議不得超出凍結範圍與 audience。中樞判斷需要更大範圍時**只回 `escalate`**，由迴圈**結束本 Run** 並送出候選事件（缺口類別＋`decision_id`）；迴圈不自行發 `LoopTrigger`，是否發新的 `LoopTrigger` 由中樞 `loop.reeval` 裁定、由套用者組裝（走 §4.6.3；Q17 因此定案為「新 Run」） |
| 預算 | consult 計入迴圈步數（`max_steps`／`max_tool_calls`，AgentLoop 強制，AL-2）；走快速欄位，**300ms 只計 `decide()`**；executor 總時限為 **0.5s**（工具層定，含 ActionIntent 管線）；不觸發 `plan.refine`；逾時／busy／invalid 回 `advice=∅`＋對應 `reason_code`（`consult_timeout`／`consult_busy`／`consult_invalid`），迴圈採用下方 fail-safe 預設值（fail-open 於「建議」，不影響硬閘） |
| 可觀測 | 結果寫入決策日誌（`decision_log`，`kind=loop.consult`、`sub_kind`、`parent_decision_id`＝觸發本 Run 的決策、`run_id`/`step_id`）；因為是 ActionIntent，receipt 與日誌以 `decision_id` 互相參照；可重播評估（相同 request＋凍結範圍＋engine 版本得相同結果），也可 shadow 另一個 engine 比對 |
| 防濫用 | consult 次數受步數預算與「無進展」偵測約束（連續相同 consult 結果不採用視為無進展）；每 Run 的 consult 上限由 `policy_ref` 解析；預設值 `MAX_CONSULTS=8`、`NO_PROGRESS_N=3`（2026-11-06 艾斯維爾裁決為正式值） |

consult 逾時或失敗時，迴圈採用的 fail-safe 預設值（`advice=∅` 時套用；全部取「最保守、不擴權、不產生新副作用」的一側，亦符合工具層「預設過寬視為擴權」的要求）：

| sub-kind | fail-safe 預設 | 理由 |
|---|---|---|
| `speak` | `hold`（本步不開口、不插話） | 不確定時不打擾；AL-4 下開口本來就非必須 |
| `output_modality` | 維持目前模態 | 不改變輸出路徑，不增加 TTS／動畫成本 |
| `placement` | 維持目前平台 | 不移轉、不改 executor；移轉屬擴張，須經中樞 |
| `ask_user` | `ask`（先問使用者） | 不確定是否該自行決定時，問的代價最低 |
| `loop_end` | `finalize`（收尾結束） | 避免無限續想；與步數預算、無進展偵測一致 |
| `followup` | 不排 | 不憑空建立後續回報；使用者可再詢問 |

數值皆沿用審查建議，未調整。這些預設屬迴圈側行為，中樞不可用時同樣適用。

與既有機制的關係：
- 與 `loop.start`（plan 區段）互補：`loop.start` 決定啟動範圍，`consult` 處理執行中的局部決定。
- 與 `loop.reeval` 的差別：`reeval` 可能導致新 Run；`consult` 永遠不改變當前 Run 的範圍。
- AL-4（想不進 Output Gate）不受影響：`speak` 建議只影響「迴圈是否產生 `result`／通知」，不直接發話。

## 5. 決策引擎分層

### 5.1 分層

```
 request ─► L0 硬約束(請求方已縮集合；中樞入口再驗) ─► 失敗 ⇒ 直接 fallback/pass
        ─► L1 規則引擎(WakeDetector、Engagement、DreamPlanner…；確定性、µs–ms)
        ─► L2 特徵抽取(英文 NLP：bio_tagger intent/BIOS 切分、command/chat 分類…)
        ─► L3 學習模型提議者(Laya／jevos 等；僅在預算與 egress 允許時)
        ─► L4 LLM(僅 async／二階段，且 llm_allowed 的 kind)
        ─► 合併策略(first-confident／加權／規則否決優先) ─► validate ─► 輸出
 shadow：任一層的候選引擎可與主引擎並行，只記錄差異
```

| 層 | 內容 | 延遲 | 失敗行為 |
|---|---|---|---|
| L0 | 約束檢查、`allowed_outcomes` 驗證 | µs | 回 `on_timeout` 預設 |
| L1 | 現有規則實作（多半已存在，直接註冊為 engine） | µs–ms | 規則例外 ⇒ fallback |
| L2 | `models/nlp/bio_tagger`（DistilBERT token classification，標籤 CALL/CHAT/DIRECT_WORK/BACKGROUND_WORK/UNKNOWN）、`command_chat_classifier`；CPU 單句約 12–13ms（DL-5 重測：p50 13.4ms／p95 17.3ms，兩模型串行含映射，見 §5.2.1） | 十餘 ms | 特徵缺 ⇒ `features.unavailable`，L1 照跑 |
| L3 | 候選：Laya-multilingual（mmBERT 322M）、jevos-v4（位置未知，見 lore note 49c70d2e 的評估計畫） | 未知（待量） | 逾時／busy ⇒ 沿用 `ProposerGuard` 立即回預設 |
| L4 | LLM | 數百 ms–秒 | 僅 async；失敗 ⇒ 保持 L1–L3 結果 |

**提議者可替換：** 沿用 `ProposerRegistry`（`proposer.py:205`）的 `proposer_id → factory` 註冊，擴成 `engine_id`；每個 kind 的 engine 鏈在設定中宣告（例：`turn.reply: [rule.v1] shadow=[rule_nlp.v1, laya.v0]`）。換 engine 不動呼叫方。現行 `turn.reply` 由 `UEP_DECISION_PROPOSER`（primary，預設 `rules.default`）與 `UEP_DECISION_SHADOW_PROPOSERS`（逗號分隔，預設 `respond.minimal`，空字串關閉）選擇；未註冊的 id 於 Host 組裝時直接報錯，Host 明確傳入的 `proposer`／`shadow_proposers`／`decision` 優先。

### 5.2 為什麼 L2 是「特徵」而不是「決策」

bio_tagger／分類器輸出的是**標籤與切分**，沒有 `reply_mode`、沒有 Risky 標註（`train/nlp` 6346 筆資料無此標註，已核對房內說明）。直接當決策會把「這句像命令」誤當「該不該回」。作法：L2 產出 `FeatureBundle`（`intent_spans`、`intent_dominant`、`confidence`、`lang`），由 L1 規則或 L3 模型**消費**；學習模型需要的 `reply_mode`／Risky 標註走第 7 節 P4 的資料收集。

#### 5.2.1 現有英文 NLP 的標籤、映射與接入（DL-5）

實作：`uep/echo/nlp_wiring.py`，以 shadow proposer `nlp.legacy` 註冊（`uep/turn/registry.py`）。預設關閉，列進 `UEP_DECISION_SHADOW_PROPOSERS` 才組裝；模型目錄 `UEP_NLP_MODEL_DIR`（預設 repo 相對 `models/nlp`，本機未追蹤資產）；模型檔缺失時工廠建立當下拋 `ValueError`。`transformers`／`torch` 只在背景 warmup 執行緒 import，CPU 推理，載入約 6 秒；warmup 或載入失敗期間回 D80 預設（`nlp_warming_up`／`nlp_load_failed`）。

**id2label（核實自 `config.json`）**

| 模型 | 架構 | id2label |
|---|---|---|
| `bio_tagger` | `DistilBertForTokenClassification`（`distilbert-base-uncased`，詞彙表 30522） | 0=O；1/2=B-/I-CALL；3/4=B-/I-CHAT；5/6=B-/I-DIRECT_WORK；7/8=B-/I-BACKGROUND_WORK；9/10=B-/I-UNKNOWN |
| `command_chat_classifier` | `DistilBertForSequenceClassification`（同底座） | `config.json` 只有 LABEL_0..2；**實測判定**：LABEL_0=command、LABEL_1=chat、LABEL_2=non-sense |

分類器標籤的依據：對 `train/nlp/dataset.csv`（824 筆：command 189／chat 203／non-sense 432）逐筆推理，三類與 LABEL_0/1/2 一對一、訓練集內準確率 100%（未做留出驗證，所以只證明對應關係，不證明泛化）。legacy 程式碼只在 `config.yaml` 列出 `intent_model_dir`，從未載入此模型，沒有第二來源。標籤順序不是字母序（字母序會是 chat=0），而是 command=0、chat=1、non-sense=2，與卡片原先的推測順序一致。

**BIO 推論細節：** 訓練時只對每個詞的第一個 subtoken 標註，推論也只取詞首 token（`word_ids`），再把連續的 B-X／I-X 合併為區段。

**映射（暫定映射，待標註集驗證）**——模型沒有學過 `reply_mode`，下表只為了讓 shadow 能與主引擎比對差異：

| 來源 | Proposal 欄位 |
|---|---|
| BIO 任一區段為 CALL | `addressed=True`（否則 False；不採用 `addressed_hint`） |
| BIO 含 DIRECT_WORK | `route=task_request`（優先） |
| BIO 含 BACKGROUND_WORK（且無 DIRECT_WORK） | `route=agent_loop` |
| BIO 只有 CHAT／UNKNOWN／無區段 | `route=direct_chat`；但分類器為 command 時補成 `task_request` |
| 分類器 non-sense | `reply_mode=pass` |
| 其餘 | `reply_mode` 沿用 D80：addressed（BIO 或 hint）或單人／人數未知 -> `respond`，多人未點名 -> `passive` |
| `confidence` | BIO 區段平均機率與分類器最大機率的平均（無區段則只取分類器） |

`reason_code=nlp_model`，`interaction_to` 恆為 None，通過 `validate_proposal`。

**語言 gating：** 只對英文打分；以「ASCII 字母數／全部字母數」≥ 0.8（`ASCII_LETTER_RATIO_THRESHOLD`）判定。非英文（含中英混雜）回 D80 預設，`reason_code=nlp_lang_unsupported`，`metrics["nlp_lang_unsupported"]` 計數。中文待 Q6=C 的兩條路（逐段 MT／Laya 多語編碼器直吃原文）shadow 後再定，本次無 MT 元件。

**延遲（DL-5 實測，本機 CPU、預熱後 200 次、含 gating＋兩模型推理＋映射）：** p50 13.4ms、p95 17.3ms、max 33.7ms。

### 5.3 規則與模型的合併

- 規則的**否決權優先**（例如被點名絕不 pass）；模型只能在規則留下的空間內加分／選擇。
- 模型輸出一律視為不受信資料，只收 schema 內列舉（沿用 P3 §4.3）。
- 新 engine 一律先 shadow，累積差異再升為主決策（沿用 ADR-011 的精神，推廣到所有 kind）。

### 5.4 內部英文與邊界翻譯

| 層面 | 規則 |
|---|---|
| 內部契約 | 所有 `kind`、`outcome`、`reason_code`、plan 欄位、特徵標籤皆英文列舉／ID |
| 原文保留 | `text` 以 ref 讀取，原文不翻譯、不改寫；journal 的 `payload_blob` 仍存原文（D33） |
| **不翻譯的路徑** | `WakeDetector`（對原文做 Levenshtein 比對，別名含「小U」，`wake.py:84`）、`GapFiller` 按 STT 語言碼選池（`gap_filler.py:128`）、人設回覆生成、使用者可見字串 |
| **需要英文的路徑** | 只有 L2 特徵抽取（現有英文 NLP；`distilbert-base-uncased`，詞彙表 30522，英文專用） |
| 翻譯位置 | **特徵抽取入口**（Boundary Translator），不在 STT 之後全域翻譯。每個 segment 於 `aggregator.feed` 時即送翻譯，與聚合視窗（250–3000ms）重疊；turn 關閉時 `text_en` 通常已備妥 |
| 延遲影響 | 不佔 `turn.reply` 的 300ms 預算（翻譯在聚合等待期間完成）；`PassThroughAggregator`（預設）沒有等待視窗時，初期 L2 以 shadow 方式進行，不阻塞主路徑 |
| 翻譯缺席 | `features.text_en` 缺 ⇒ L2 標 `unavailable`，L1 規則照跑（不因翻譯失敗拖垮決策） |
| 替代 | 多語言編碼器（Laya mmBERT）可跳過翻譯直接吃原文，屆時 Boundary Translator 對該 engine 變成 no-op |
| 翻譯回程 | 使用者可見字串（含暫態訊息、墊片音）由輸出邊界以人設語言產生；plan 內不放字串，只放 `interim.kind` 與模板 ID |

> 【奈也】翻譯成英文讓現有的 NLP 直接能用，這是最快有成果的路。
> 【奈留】但中英文語意差異會把誤差帶進決策：「欸，你那個」「小U」這類指涉詞翻譯後會失去可比對性，所以喚醒與指涉判斷必須留在原文。我也不確定本機 MT 在 CPU 上單句的延遲（常見是數十到兩百 ms，未實測），因此不替艾斯維爾選，列 Q6。

## 6. 關鍵決策（ADR）

#### ADR-01：中樞是獨立葉節點套件，in-process 起步，協定可抽離
- 背景：需求要求「獨立的決策系統」，不在輸入→輸出流程中。
- 決策：`uep/decision/`（contracts 為葉節點）；首版同一行程，以 `DecisionClient` port 呼叫；契約不含 Python 專屬型別，之後可改成跨行程。
- 奈也觀點：先在行程內做出來，模型服務（Laya／LLM）再獨立成服務，符合提案 ADR-002「模組化單程序＋模型服務分離」。
- 奈留觀點：獨立的重點是**依賴方向**，不是行程邊界；現在就拆服務會把 300ms 預算花在序列化上。
- 替代方案：獨立微服務（延遲、營運成本高）；放回 Orchestrator 內（現況，無法容納輸出側與主動）。
- 後果：Orchestrator 變成中樞的一個客戶；`uep/turn/` 的決策實作搬為 engine 註冊。

#### ADR-02：硬閘不收編；中樞只在請求方縮好的集合內選
- 背景：全系統決策容易滑向「中樞統一裁決」。
- 決策：A 層維持原權威；Output Gate 不是決策點（D73 已定逐句 dispatch、增量上限 +150ms，再加一跳會破壞預算）。中樞只決定「要不要產生 intent、kind、style」。
- 奈也觀點：保留現有 Gate 讓 P3 已驗收的路徑不動。
- 奈留觀點：授權只能有一個權威。中樞若可 admit，等於第二套 Gate，必然分歧。
- 替代方案：中樞先審 OutputIntent 再給 Gate（雙閘，延遲加倍）。
- 後果：`constraints` 產生 helper 成為關鍵點（§2.3）。

#### ADR-03：熱路徑以發布快照取代逐事件請求
- 背景：barge-in／讓位每個音訊 chunk 判斷，且必須同步、純計算、不得 I/O（P3 §4.4）。
- 決策：中樞對 B 層只輸出 `PolicySnapshot`（沿用版本、`ttl_s`、平台 preset、`mode_rules`）；ES 內機制不變。模型若要調讓位門檻，只能調快照參數。
- 奈也觀點：這讓「模型調參」有了安全路徑：改的是數字，不是即時決策。
- 奈留觀點：快照過期語意（Q-5：退保守）必須是中樞的契約義務，不是消費者的臨時決定。
- 替代方案：B 層嵌入小模型（延遲與執行緒風險）。
- 後果：`policy.snapshot` 為 publish kind，`HostPolicySource` 成為其發布端。

#### ADR-04：中樞只提議 provisioning，不「安裝」
- 背景：艾斯維爾要求依意圖預先安裝並啟動模組。
- 決策：plan 的 `action` 只有 `keep／warm／load／unload`（對**已註冊、已安裝**的模組）。「安裝新模組」屬供應鏈風險（提案 §18），歸 module coordinator＋Task Manager＋approval（高影響類），中樞最多提出「建議安裝」的候選事件，經核准流程。
- 奈也觀點：使用者說「幫我整理照片」時能直接預熱相關工具，體感會好很多；安裝需要確認是合理的。
- 奈留觀點：模型推測意圖後自動安裝，等於用機率值換取程式碼執行權，這條線不能讓。
- 替代方案：中樞可直接 install（拒絕：違反 §18.2）。
- 後果：中樞提議、module coordinator 執行，工具註冊表只維護 readiness（Q5 已定案、Q19）；module coordinator 本體待設計。

#### ADR-05：決策可被重新請求，但擴權必經候選事件
- 背景：新架構不是單向流程。
- 決策：`trigger=reeval` 的請求必須帶 `parent_decision_id` 與新的 `snapshot_versions`；結果以 `plan_version` 遞增取代舊版；任何擴大 capability 的重新決策只能由「候選事件」觸發，不由迴圈直接呼叫。
- 奈也觀點：這讓使用者感覺「她會邊做邊想」。
- 奈留觀點：必須有重請求次數與預算上限，並在日誌中形成可追溯的鏈（`supersedes`）。
- 替代方案：計畫一次定死（簡單但無法處理缺能力）。
- 後果：`loop.reeval` 為正式 kind。

#### ADR-06：翻譯只服務特徵支路
- 見 §5.4。決策：Boundary Translator 位於特徵抽取入口；原文路徑不經翻譯。替代：全域 STT 後翻譯（喚醒與語言碼比對會壞）。

#### ADR-07：決策日誌用專用表，journal 只放關鍵事件
- 背景：每次決策都入 journal 會膨脹並引入隱私面。
- 決策：`decision_log` 專表（無原文）；journal 只發 `turn.skipped`、`proactive.candidate_decided`、`decision.made`（精簡 payload）。shadow 不入 journal。
- 替代：全部入 journal（重播最完整，但量大、風險高）。

## 7. 與現行程式的遷移路徑

原則：每階段**行為可驗證等價**或以 shadow 並行；不一次改兩個層。

| 階段 | 內容 | 行為變化 | 驗收 |
|---|---|---|---|
| **P0 包裝** | ①新增 `uep/decision/`：contracts、registry、`DecisionClient`。②`TurnOrchestrator._propose`（`orchestrator.py:526`）改呼叫 `hub.decide("turn.reply", …)`；中樞內部沿用 `ProposerGuard`（`proposer.py:136`）、`ProposerRegistry`（`proposer.py:205`）、`fallback_proposal`（`proposer.py:104`）、`validate_proposal`（`proposer.py:114`）、`_run_shadows`＋`ShadowRecord`（`orchestrator.py:598,145`）。③`Proposal` ↔ `DecisionResult` 雙向轉換（`Proposal` 暫保留，plan 只填 `route`、`reply.mode`、`interaction_to`）。④新增 import 邊界測試 | **零變化** | 現有 `tests/uep/` 全綠；同請求在包裝前後 outcome／reason_code 完全一致；逾時／busy／invalid 三種 fallback 計數鍵不變 |
| **P1 收編輸出與排程** | `RuleProposer.tick`→`turn.interject`；`ModeController`＋`HostPolicySource.publish_channel_mode`→`channel.mode`/`policy.snapshot`（publish）；~~`GapFiller._pick_text`→`filler.pick`~~（取消，Q-6）；`DreamPlanner.decide` 註冊為 `memory.dream` 的規則 engine（`DreamLoop` 變成客戶；shadow 預設沿用 D100）。組裝 `RuleProposer`（現未組裝）以 shadow 先行 | 無（逐點 shadow 比對後才切） | 每點 shadow 一致率 ≥ 95%（2026-11-06 艾斯維爾裁決）；`channel.mode`／`policy.snapshot` 沒有第二套規則可比，改以不變量審計（版本連號、ES 與 Core 同版、模式一致，initial 只能是第一筆）驗收；Gate 不動 |
| **P2 計畫** | 引入 `DecisionPlan` 區段：`route` 開始有消費者（與工具層的 `capability_hint`、預設標籤表、`task_request` 對齊）；`reply.delivery`、`interim`、`output`；`plan.refine`＋`provisioning`（warm／load 已安裝模組）；`placement`（先只讀、只記錄＝shadow）。`loop.start`／`loop.reeval` 與 Agent 迴圈接上 | 有（但每個區段先 shadow） | 工具層驗收（TG-12／PD-9 的交集規則）；暫態訊息語意（Q8）已定 |
| **P3 主動與位置** | `proactive.initiate`、`presence.join_or_move`（D84 加權、冷卻）、`report.route`；強制先 shadow 並記「會不會提醒／為什麼」 | 有（限縮、可關） | 誤打擾／漏報觀察期 |
| **P4 學習模型** | 接 L2 特徵（先 shadow）、再接 L3（Laya／jevos）；訓練資料以 `decision_log` 的後驗標籤補 `reply_mode`／Risky 標註；多語編碼器評估 | 有（shadow→灰度） | 選型證據：延遲、一致率、誤判類別 |

**P4 現況（DL-2，shadow 殼）：** `laya.shadow`（`uep/echo/laya_wiring.py`，已註冊於 `PROPOSERS`）只作 shadow，預設關閉，需把它放進 `UEP_DECISION_SHADOW_PROPOSERS` 才組裝；`laya` 套件只在該模組內延遲 import，未安裝時工廠拋 `ValueError`（啟動即報錯）。權重放在使用者目錄、不走 HF 快取：`UEP_LAYA_MODELS_DIR`（預設 `~/.uep/models/laya`，比照 `UEP_TTS_MODELS_DIR`），`UEP_LAYA_MODEL` 未設時載入 `<UEP_LAYA_MODELS_DIR>/laya-multilingual`（解參照後的 HF snapshot 實體檔，目錄內 `REVISION` 檔記錄來源 snapshot 雜湊，作為 `version` 的 revision）；該目錄不存在時工廠建立當下拋 `ValueError`，不自動退回 hub 下載。`UEP_LAYA_MODEL` 明確設成 HF id（如 `convaiinnovations/laya-multilingual`）或其他路徑則照原樣傳給 `laya.load`。其他組態：`UEP_LAYA_REVISION`（選填，固定 hub 模型版本；預設本地目錄時不使用）、`UEP_LAYA_DEVICE`（預設 `cuda`，不可用時退回 `cpu`）。模型在 proposer 建構時由背景執行緒載入，warmup 期間與載入失敗後 `propose` 立即回 D80 預設並計數（`laya_warming_up`／`laya_load_failed`），不佔 300ms 預算。送入模型的 state 只含助理名稱、泛稱說話者、在場人數與本句文字，不含 `speaker_ref` 與 Risky／秘密欄位。laya 版本尚未定（0.4.22 或 0.4.30，adapter 兩者相容），專案未安裝 laya，且仍需微調。零樣本評估數據：GPU 三題 p95 約 102ms、CPU p95 超過 400ms（超出預算，只能 shadow）；`reply_mode` 零樣本不可用，需以 `decision_log` 後驗標籤微調後再談灰度。

P0 的最小內容（供任務卡拆解）：契約型別、registry、`decide()` 同步路徑＋shadow 掛點、`Proposal` 轉換、測試。其他階段各自另立任務。
