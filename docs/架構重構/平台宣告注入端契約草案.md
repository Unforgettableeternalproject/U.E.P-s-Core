## 2. 型別與語意

### 2.1 current_platform 語意

- 定義：`current_platform` = 該 persona 的 Presence 為 **ACTIVE 時的 `location`**；Presence 非 ACTIVE（NONE／RECOVERING）則為 None。**（Bernie 11/10 更正：休眠走 Behavior=SLEEP，Presence 仍為 ACTIVE；NONE 僅表示系統未啟用或不可用，如尚未啟動、移轉失敗、安全停止；系統運作期間任一時刻恰有一筆生效中的 PresencePlan。）**這與 `ProactiveContext.current_platform` 同義，三個消費點同一語意。
- `session.platform` 不是 current_platform。它是「這一輪輸入從哪來」（輸入端平台），可以和 Presence 位置不同（例：Presence 在 desktop，使用者從 Discord 發訊）。
- 關係：兩者獨立並存；PlatformContext 同時攜帶 `session_platform` 供場域類判定（PD-9 第 4 點的 venue），但**投影與 placement 只用 current_platform**。
- 【奈也】使用者從 Discord 說話、Presence 在 desktop 時，要不要讓模型看到 Discord 變體？首版不要，行為先守住。【奈留】兩個來源各自入欄位但不混用，混用就是日後的靜默 bug。
- `presence_active_platforms` = `{current_platform}`（Presence 單一 ACTIVE 位置，所以集合至多 1 個）。

### 2.2 資料形狀

```python
# 放置：uep/contracts/platform.py（新檔，與 contracts/presence.py 同層，端點與 Core 同源引用）
# 只放純資料，不 import tools／decision／presence（依賴單向）。

PlatformId = str  # 小寫、字元集 [a-z0-9_.:-]{1,64}，與 loop_consult._SAFE_REF 同；映射 PresenceLocation.value

@dataclass(frozen=True)
class ExecutorDescriptor:
    executor_ref: str          # PD-18：tool:platform，例 "member_recall:discord"；符合 _SAFE_REF，不得含 "@"
    tool: str                  # 對應 registry 條目名
    platform: PlatformId       # 變體所屬平台
    origin: str                # "registry_static"（階段 A）| "platform_declared"（階段 B，且已核准）| "coarse_fallback"（F-1）

@dataclass(frozen=True)
class PlatformDeclaration:     # 階段 B 才有真實資料；階段 A 由 registry 靜態推導，欄位可為空
    platform: PlatformId
    online: bool
    declared_tools: frozenset[str]
    declaration_revision: int  # 增補 §declare 的 declared_revision

@dataclass(frozen=True)
class PlatformContext:         # 單一快照；三個消費點只讀它
    version: int               # 見 §3.3
    presence_generation: int   # 取自 PresenceView.generation（無 Presence -> 0）
    presence_row_version: int  # 取自 PresenceView.row_version
    presence_status: PresenceStatus
    current_platform: PlatformId | None
    presence_active_platforms: frozenset[PlatformId]
    session_platform: PlatformId | None   # 已映射；不可映射 -> None
    available_executors: tuple[str, ...]  # 排序、去重；只含 current_platform 的變體
    registry_revision: int     # ToolRegistry 投影 revision（readiness）
    declaration_revision: int  # 階段 A 恆 0
```

- 為何放 `uep/contracts/`：決策層（`loop_consult`、`proactive`）與工具層（`projection`）都需要型別，不能互相 import（決策層不 import tools，反之亦然）。`contracts/presence.py` 已是同類先例。
- 與 PresenceLocation 關係：`PresenceLocation` 保留為「Presence 可選位置」閉集；`PlatformId` 為開放字串，因為增補允許 P3 後新增平台。映射 `PresenceLocation.value -> PlatformId` 為恆等。ProactiveContext 內部維持 enum，**組裝層**負責 `PresenceLocation(ctx.current_platform)` 的轉換（反向：非閉集平台 -> 該欄位為 None 並記 shadow 差異）。
- 【奈留】`available_executors` 型別在 loop_consult 是 `list[str]`，PlatformContext 內用 tuple，分發時轉 list，不改 loop_consult 契約。

### 2.3 available_executors 的內容（粗粒度）

- 規則：對每個 registry 可見、readiness 非 `unavailable`、且 `scope.variants` 含 `current_platform` 的條目，產生一個 `executor_ref = f"{tool}:{current_platform}"`（`:` 合法，`@` 不合法）。
- 只收 current_platform 的變體（工具層粗粒度做法）。無變體但 `scope.platforms` 含 current_platform 的條目：首版**不收**（無 executor 可換，換了等於沒換）；列為 DQ-2。
- 階段 B：再與 `PlatformDeclaration.online` 且 `declared_tools` 交集（對應增補 PD-9 第 2、3、5 點）。離線＝清單為空，loop_consult 走 `scope_exceeded` fail-closed。
- F-1 退路（工具層）：若 executor 粒度對不上，`available_executors` 退化為 `(current_platform,)` 單元素，即「只能留在原 executor」，等價於 Q26 的最保守。這是退路，不是預設。

## 3. 單一注入路徑

### 3.1 責任劃分

```
 [PresenceManager.current()]──┐                      組裝層（唯一計算點）
 [session.platform]──────────┼──> PlatformContextProvider.snapshot(turn_ref) ──> PlatformContext (frozen)
 [ToolRegistry 條目＋readiness]┤                              │
 [階段B: ConnectionDirectory]─┘                              ├─> (1) ProjectionContext     (工具層建構子，純函式轉換)
                                                              ├─> (2) loop_consult facts    (注入；覆蓋模型值)
                                                              └─> (3) ProactiveContext      (組裝層欄位填入)
```

- `PlatformContextProvider` 屬**組裝層**（uep/agent 或 uep/echo 的 wiring；與 `*_wiring.py` 同層）。它是唯一同時可 import presence、tools、contracts 的地方。決策層與工具層只拿到 `PlatformContext`（或其投影），不拿 provider。
- 轉換函式（各在消費者那一層，純函式、不查 Presence）：
  - `ProjectionContext.from_platform(pc, *, available_context, audience)`（工具層；補一個 classmethod 或模組函式，不改欄位）。
  - `placement_facts(pc) -> {"current_platform":…, "available_executors": list(…)}`（決策層，loop_consult 模組旁）。
  - `proactive_presence_fields(pc) -> dict`（決策層；填 `presence_status`、`current_platform`、`presence_generation`）。
- 禁止：任何消費點自行呼叫 `PresenceManager.current()` 或 registry 去算平台。以 AST／grep 測試強制（比照 `test_import_boundary.py`）。

### 3.2 計算時機

| 時機 | 誰算 | 內容 |
|---|---|---|
| 每個 turn 開始（Host 進入 `_run_tool`／`_refresh_tools_agent` 之前） | provider.snapshot() | 讀 `PresenceManager.current()` 一次、registry readiness 一次，產出 PlatformContext |
| 同一 turn 內的所有 `project`、`consult` | 不重算 | 沿用該 turn 的快照（turn_scope 持有）；AL-3 單調性要求同 turn 脈絡不抖動 |
| Proactive 評估 | provider.snapshot() | 自己一份（無 turn），但 `proactive.initiate` 的事實與 placement 注入共用同一份 |

【奈留】不可「每次 project 都現讀 Presence」：`current()` 在過期時會進鎖定交易寫入（`manager.py:364-375`），在熱路徑會有副作用與延遲。快照每 turn 一次即可。

### 3.3 version、generation、刷新

- `PlatformContext.version`：provider 內部單調遞增整數；當且僅當 `(presence_generation, presence_row_version, presence_status, current_platform, available_executors, registry_revision, declaration_revision)` 與上一份不同時 +1。
- 注意：`generation` **只在核發 Lease 時 +1**，撤銷／過期／釋放不再 +1（`manager.py:9、:517`）。所以位置變化（新核發）看 generation，但 ACTIVE -> RECOVERING／NONE 的轉換 generation 不變，必須同時比對 `status`；`row_version`（`manager.py:248-250` 每次寫入 +1）可作為「Presence 有任何變動」的廉價訊號，列入 version 判定。不另訂訂閱機制（首版輪詢式：下個 turn 自然取到新值）。
- 平台加入／離開（階段 B）：`ConnectionDirectory` 的 `declaration_revision` 變動 -> 下個 snapshot 才反映；同 turn 內不變，但執行期仍由 `executor_ready`（PD-10）重驗，不依賴快照。
- 與 AL-3 的關係：`prior` 單調保證「同 Run 內脈絡只能收窄」。平台離開 -> 清單縮小，合規；平台加入 -> 新工具被 `prior` 剔除並列入 `narrowed_by_prior`，合規且已有現成機制，**不需新增規則**。
- 【奈也】使用者在 turn 中途切換位置時，新位置要下個 turn 才生效，可接受。【奈留】Run 內 Presence 位置改變時，`placement` consult 的 `current_platform` 與當下 Presence 可能不一致；consult 需把 `platform_context_version` 寫進 decision log（`decision_log` 欄位，`0014_decision_log_columns`）以便稽核，不用新 migration 的做法見 §6。

### 3.4 失敗語意（fail-closed）

- 讀 Presence 失敗／未 start（`PresenceNotStarted`）：`current_platform=None`、`available_executors=()`、`presence_status=NONE`，並記錄 warning；不拋給 turn。
- 結果等同今日行為：projection 無場域、placement 回 `placement_review`／`scope_exceeded`。**這就是「零行為變化」的退化落點。**
- 映射失敗（session.platform 無法映射）：`session_platform=None`；不影響 current_platform。

## 5. 與 migration

- 預設：**不需要**。PlatformContext 為每 turn 記憶體快照，不持久化；version 為 provider 行程內計數，重啟歸零（比較用 `presence_generation` 與 `declaration_revision`，兩者本身持久）。
- 決策 log 要記 `platform_context_version`：優先放既有 JSONB／payload 欄位，不加欄（需先確認 `0014_decision_log_columns` 是否已有 payload 欄；未驗證）。
- 若上述不可行，或階段 B 要持久化平台宣告與核准清單版本：**需從 0018 起，先在房內講**（目前 head 為 0014，0015～0017 視為其他在途占用）。本草案不含。
