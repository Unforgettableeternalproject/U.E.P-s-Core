## 1. 名詞定義與權責

| 名詞 | 定義 | 能做 | 不能做 |
|---|---|---|---|
| 主機（Host） | Mac mini 上的 Core 裁決中樞。Presence=NONE 時她所在之處 | 裁決轉移／指示；唯一寫入 Presence（Presence Manager）；執行內部活動（做夢、記憶整理）| 沒有任何對外輸入輸出通道；不以「主機」身分對任何平台說話 |
| Presence | 她此刻能以本人身分互動的**平台**（`desktop｜discord｜website`）或 NONE（在主機）；最多一個（INV-01）| 決定互動／輸出是否成立 | 不由 Adapter 自報（INV-04）；不細到頻道／裝置 |
| Activity | 她正在做的事（對話、桌面工作、做夢…），可多項；帶更細的位置（頻道、裝置）| 展示用途；`presence_bound` 判定依據 | 不是位置權威；不能核發 Lease |
| 行程（PresencePlan） | 她「應該」在哪、做什麼；總是存在；行程的 NONE＝不可用 | 提出意向（第一階段轉移的唯一來源）| 不核發 Lease（§12.4）|
| Behavior | 她當下怎麼表現（CHAT／WORK／MISCHIEF／SLEEP 僅為候選）| 由主機合理化行程建議 | 本契約不定義 |
| **監控端點（monitor）** | 平台上的**非本人**介面，兩個功能：(a) 只讀狀態顯示；(b) **缺席端受限輸入通道**（F5）| 顯示分級狀態；把入站項目原樣轉發核心；回中性系統回條 | 產生 `UtteranceFact`、開 turn、以她的身分回話、作為 `source_location`／Presence 依據、持有 Lease 或授權六元組、錄音／語音、**在平台端判斷意圖或授權** |
| **互動端點（interaction）** | 平台上**她本人**的介面（文字、語音、avatar、前景桌面工具）；只在 Presence ACTIVE 於該平台時成立 | 持有 Lease；收 utterance、開 turn；承載 OutputIntent | 在非 ACTIVE 時收發任何角色內容；自行 acquire 取得位置（見 §6、風險 R1）|
| 輸出端點（output） | 互動端點的輸出面（sink／播放器／typing／動畫）| 通過 Gate＋端點二次接納後發出 | 同上；另外不得回送系統回條冒充她（O-8）|

【奈留】一個平台 adapter 是**一個連線身分、兩種能力面**：能力面各自宣告、各自授權、各自審計；權限不得因同一連線而互通。

## 2. 端點註冊時的能力宣告

### 2.1 資料形狀（純資料；實作於 `uep/contracts/platform.py`，E1）

現況：`PlatformDeclaration` 只有 `platform／online／declared_tools／declaration_revision`；提案 §13.1 的 capability 清單（`audio_in／audio_out／text／avatar／desktop_tools／delivery_receipts`）原無對應型別。`online` **保留，只表示連線**（Q12 A），能力面另列。

```python
MonitorFacet = Literal["status_view", "health_view", "activity_view", "instruction_inbox"]
InteractionFacet = Literal["text", "audio_in", "audio_out", "avatar", "desktop_tools", "delivery_receipts"]  # 沿用 §13.1

@dataclass(frozen=True)
class MonitorSurface:
    surface_ref: str                           # 例 "discord:chan_x"、"web:admin"（SAFE_REF 字元集）
    audience_cap_claimed: str                  # 平台自稱：public｜group｜private（僅為宣告，Core 以核准設定為準，M-4）
    operator_auth: Literal["none", "platform_identity", "owner_channel"]  # 辨識「指示者」的方式

@dataclass(frozen=True)
class MonitorCapability:
    facets: frozenset[MonitorFacet]
    surfaces: tuple[MonitorSurface, ...]

@dataclass(frozen=True)
class InteractionCapability:
    facets: frozenset[InteractionFacet]

@dataclass(frozen=True)
class PlatformCapabilities:
    platform: PlatformId
    endpoint_instance_id: str
    protocol_version: int
    monitor: MonitorCapability | None          # None＝此連線不提供監控
    interaction: InteractionCapability | None  # None＝此連線不提供互動（例：純 Web 管理頁）
    declaration_revision: int = 0
```

registry 側（Core 側核准清單，與 PD-17 同權：只有艾斯維爾可改）：`PlatformEndpointPolicy`（待實作）= `{platform, monitor_surfaces: {surface_ref → audience_cap, allowed_instruction_kinds}, interaction_allowed: bool}`。**請求者身分映射不放在此處**，走 `platform_links` 設定檔（Q9 A，§4.5）。宣告只表示「技術上能做」，核准設定才表示「允許」（§13.1）。

### 2.2 規則

| 編號 | 規則 | 依據 |
|---|---|---|
| EC-1 | 同一連線可同時有 `monitor` 與 `interaction`；兩者**分開宣告、分開核准、分開撤銷**。缺省（未宣告）＝無該能力 | F1、PD-1 精神 |
| EC-2 | `monitor` 能力不得產生 `UtteranceFact`；其入站訊息型別只能是 `AbsentInboundItem`（§4.3），沒有 `speaker_ref→turn` 路徑 | F5、F6 |
| EC-3 | `monitor` 的任何事實（連線在線、heartbeat、使用者在線狀態）不得用於 `current_platform`、`presence_active_platforms`、`source_location`、`user_present`。`PlatformContextProvider` 的 `current_platform` 仍**只**來自 `PresenceView` | F6、DQ-1-A |
| EC-4 | 宣告 `interaction` 也**不等於**可 acquire：acquire 需主機裁決（§6.2）；平台連線 ONLINE（PD-9 第 3 點）只是工具可見性的必要條件，不是 Presence | INV-04、§10.3 |
| EC-5 | 重連＝全量重宣告（沿用 PD-6）；兩種能力面都不沿用舊連線宣告 | PD-6 |
| EC-6 | 宣告內文屬不可信資料（沿用 PD-2／PD-15）；`audience_cap_claimed` 只可**收窄**實際上限，不可放寬 | PD-15 |

【奈也】宣告型別長得像「兩張清單」，前端同事一看就懂；Web 管理頁只填 `monitor`，Desktop client 兩個都填。
【奈留】不要為此新增第二套連線表；Connection Registry 的 `platform.declaration_received` 事件 payload 直接多帶 `capability_hash`（PD-2 已規定只放 ID 與雜湊）。

## 3. 互動與輸出的成立條件（Lease／generation／fence）

### 3.1 狀態矩陣

| Presence 狀態 | 該平台 interaction | 其他平台 interaction | 所有平台 monitor |
|---|---|---|---|
| ACTIVE @ X（Lease 有效）| 成立：收 utterance、開 turn、承載 OutputIntent（過 Gate＋端點二次接納）| 不成立（缺席端）| 皆可：狀態＋指示通道；X 上的 monitor 輸入**仍算缺席端輸入**（F6）|
| NONE（她在主機）| 不成立 | 不成立 | 皆可：這是唯一與她有關的介面 |
| RECOVERING | 不成立（Gate 拒絕）；只做停止／清空 | 不成立 | 皆可；顯示「復原中」|
| 移轉中（transfer phase）| 舊端：新 admission 關閉、等 quiescence；新端：`confirm_activated` 前不成立（P-8、INV-08）| 同左 | 皆可；顯示 phase（不含內容）|

### 3.2 Lease／generation／fence 的套用

| 規則 | 內容 |
|---|---|
| IC-1 | 互動／輸出的授權＝授權六元組（`persona_id, endpoint_id, lease_id, fencing_epoch, core_epoch, presence_generation`）＋ `status=ACTIVE` ＋ audience（現況 `uep/presence/gate.py`）。**只有 interaction 面持有**；monitor 面沒有 Lease、沒有六元組 |
| IC-2 | monitor 出站（狀態推播、回條）**不走 `OutputIntent`／Gate**（那是「角色可見輸出」，INV-02）；走獨立 `MonitorFrame`（系統來源，O-8：不得用 Persona 語氣）。`MonitorFrame` 帶 `state_revision`，不帶 fence；重連一律先送全量快照再接增量（§13.1），舊 revision 丟棄 |
| IC-3 | **【Q6 A】** Gate 新增前置檢查（E3 shadow 已落地，強制開關未開）：`OutputIntent.endpoint_id` 必須註冊為具 `interaction` 能力；否則拒絕，**新增拒絕碼 `REJECT_NOT_INTERACTION`**，並同步 D28 碼表（`uep/contracts/presence.py` 的 `GateDecision` 與 Core契約 §4.4 碼表）|
| IC-4 | 一個 `endpoint_id` 在 Presence 內是互動端點身分；監控連線另用 `monitor_ref`（不同命名空間），避免「同一 id 同時被當成位置持有者與監控者」|
| IC-5 | 轉移時：舊 generation 的 interaction 輸出關閉；monitor 不受影響且不需 quiescence（它沒有輸出權）。不得因監控連線存在而推論「舊端已停止」 |
| IC-6 | Lease 過期／撤銷／全域停止：interaction 立即失能（本地 watchdog，§11.4）；monitor 不降級，改顯示「她已回到主機」|

## 4. 缺席端受限輸入通道（「懶惰的輸入監控」，F5）

### 4.1 性質

| 項目 | 規定 |
|---|---|
| 地位 | monitor 端點的第二個功能面 `instruction_inbox`；Presence 為 NONE 或在他處時唯一的入站路徑；Presence 即使 ACTIVE 於同平台，經此通道入站的仍是缺席端輸入（F6）|
| 平台端只做 | 認證 actor（平台 ID）、組 `AbsentInboundItem`（原文存可刪 blob、只送 ref／長度）、**原樣轉發到核心**。**不在平台端辨識意圖、不判斷授權、不回應內容**（Q3 修正）|
| 核心端做 | 與她在場時一樣交給核心：**由核心判斷**這是否為到場請求（意圖，**可用模型**）；授權另算（§4.4）。判斷時**不開她的 turn、不載入人格輸出**，原文不落地（只有 ref／長度／判斷結果入 shadow 紀錄）|
| 不做 | 不開 turn、不產生 `UtteranceFact`、不以她的身分回話、不錄音／不參與語音 |
| 「懶惰」的意涵 | 監控面不常駐模型、不做語意；核心端的判斷是按需呼叫（單次、無對話歷史、無人格）；判斷失敗＝丟棄或留言，**不升級成 turn**；失敗不重試、不追問 |

### 4.2 指示白名單（Q2 B）

| 指示 | 狀態 | 說明 | 授權要點 |
|---|---|---|---|
| `request_presence_move`（到場／移轉請求：`target_platform`，可含 `reason`）| **首要，納入** | 請求把 Presence 移到某平台，或移回主機 | **第一階段只受理 owner（F10）**；來源／權限／優先度由主機裁決；不是直接 acquire（§6.2）|
| `request_leave`（回主機）| 納入（為前者的對偶，Q2 B「回主機」）| 等同移轉目標＝主機 | 同上 |
| `leave_message`（留言，不期待即時回覆）| 納入；**非 owner 的唯一出口之一**（另一為中性回條）| 存為待讀留言，不開 turn；§10.3「文字留言／到場請求可接收」| 內容屬 private 者只存不顯示於公開面 |
| `query_status`（查詢）| 納入 | 回分級狀態（§7）| 受 audience 分級 |
| `cancel_request`（撤回自己先前的請求）| 納入 | 只能撤回自己的 | 以 `requester` 比對 |
| 一般對話／閒聊／自由指令 | **不接受** | 丟棄或留言＋回條「她目前不在此處」| 不得因文字像問句就升級 |
| 任何工具／任務指令（執行動作、改設定、輕量系統指令如暫停提醒）| **不接受**（本期，Q2 B 不含 C）| 需另開契約（權限矩陣）；presence_bound 工具在缺席端不可觸發 | — |

**非 owner（含認證過的一般成員）的請求只能是 `leave_message` 或收到中性回條，不建立 `PresenceRequest`**（F10；更正草案 §7.2 表格「member 可送 `request_presence_move`」與 F10 的矛盾）。

### 4.3 `AbsentInboundItem` 與裁決請求（純資料；實作於 E1）

```python
@dataclass(frozen=True)
class AbsentInboundItem:            # monitor 入站唯一型別；不是 UtteranceFact
    source_platform: PlatformId     # 輸入來源（source_location）；只描述來源，不代表在場
    surface_ref: str
    actor_ref: str                  # 平台**認證過的 ID**，如 "discord:123"；絕不使用顯示名稱／暱稱比對
    actor_authenticated: bool       # 該 ID 是否由平台認證來源取得（非訊息文字自稱）；與 V18 shadow 紀錄同名
    is_owner: bool                  # 由 Core 依 platform_links（§4.5）核准映射計算，非平台自報；未認證者恆為 False
    raw_ref: str                    # 內文走可刪 blob 引用，不入 payload（比照 D78）
    length: int
    received_at: datetime

@dataclass(frozen=True)
class PresenceRequest:              # 提交主機裁決的請求（Presence Manager 之外的仲裁器消費）
    request_id: str                 # 冪等鍵：platform:surface:message_id
    source_platform: PlatformId     # 來源（F4）；owner 後台為 "owner_console"（Q5 A）
    requester_ref: str
    actor_authenticated: bool       # 只能由已認證 actor 建立：建構時必須為 True
    authority: Literal["owner", "system"]   # 第一階段只有 owner／system；member／guest 不建立請求
    priority: int                   # 優先度（Core 計算；順序：系統緊急 > 艾斯維爾 > 一般系統 > 行程）
    target: PlatformId | Literal["host"]
    reason_ref: str | None
```

E1 建構檢查（fail-closed，`ValueError`）：`AbsentInboundItem` 不存原文（`raw_ref` 限小寫安全字元集，含空白或中文即拒）、`length >= 0`、`received_at` 須帶時區、`is_owner` 為真時 `actor_authenticated` 必須為真；`PresenceRequest` 的 `actor_authenticated` 必須為真、`authority` 限 owner／system、`priority >= 0`。

### 4.4 與決策層 V18／absent_input／shadow 紀錄的銜接

| 銜接點 | 規定 |
|---|---|
| 主入口 vs 後備 | **主入口＝監控面的 `AbsentInboundItem`**（不經 `UtteranceFact`）。V18 的 `TurnOrchestrator._absent_input_reason`（`presence_inactive`／`absent_platform_input`／`source_location_missing`）是**後備關卡**：萬一缺席端文字誤經 interaction 路徑進來，仍在 propose 之前被否決 |
| shadow 紀錄 | 沿用 V18 `turn.skipped`（不新增 migration），只存 `ref`、`length`、`source`、`actor`、`actor_authenticated`、`is_owner`、`presence_request`；不含內文。**本通道的每筆入站，不論是否判斷為到場請求，都先寫同一種 shadow 紀錄**，再決定轉 `PresenceRequest`／留言／丟棄 |
| 兩條路徑的關係 | `shadow 紀錄`＝觀察用，不影響行為；`PresenceRequest`＝有後果的提交。分開寫，避免「紀錄」被誤當成「已受理」 |
| 回條（Q8 A）| 受理／拒絕／排隊皆回中性模板（「已收到到場請求」「目前無法受理」），帶 request_id；**走監控出站（IC-2），固定模板、不經 Gate**，僅限模板＋ID、禁止私人內容、不用她的口吻；可由設定關閉（§10.3），需速率限制（R5）|
| 主機裁決 | `PresenceRequest` 交由仲裁器（尚不存在）比對行程與優先度；結果：`ACCEPTED_TRANSFER／QUEUED（等安全點）／DEFERRED（SLEEP 當輪做夢完成後）／REJECTED(reason_code)`。裁決後才可能呼叫 Presence Manager（唯一寫入者）。同優先度 FIFO、逾時（預設 10 分鐘）失效，Bernie 的請求永遠插隊（Q10 A）|
| 意圖判斷（Q3）| **意圖由核心判斷（可用模型）；授權只來自已認證 actor 與規則。** 模型輸出只能是白名單指示列舉值（§4.2）＋參數，**不能產生、提升或改寫授權**（§18.3）；模型誤判最壞結果＝一筆被拒的請求或一則留言 |
| 受理條件 | `actor_authenticated ∧ is_owner`（由 Core 依 `platform_links` 計算）才建立 `PresenceRequest`；其餘（認證過的一般成員、未認證者、僅顯示名稱或訊息文字自稱像 owner 者）只寫留言或回中性回條 |

【奈也】使用者體驗：Bernie 在 Discord 傳一句「去 desktop」，不必記指令格式，核心理解後回條立刻說「已受理，等待安全點」，不需要她醒著。
【奈留】意圖放核心、授權放規則，兩件事刻意拆開：模型可以聰明，但只影響「歸類」，不影響「准不准」；prompt injection 面積限於歸類結果，且歸類結果仍要過 `actor_authenticated ∧ is_owner`。

### 4.5 身分來源（Q9 A）

請求者身分映射走 `platform_links` **設定檔登記**（預先登記 Bernie 的 Discord user ID；後台一次性綁定流程為後續）。`owner_console`（後台管理介面）經人類認證，不屬任何 Presence 位置。Core 依映射重建 `actor_id`／`is_owner`；平台連線只能斷言自己 `platform_id` 命名空間的外部 ID（PD-15 b）。
