# Phase 2 第一塊：檢索驗證（2026-08-07）

`phase15-evaluation.md` 的結論是「瓶頸不在抽取，在檢索」——抽了記憶召不出來，
跟沒抽一樣。這份是檢索的第一次實測。

## 設定

**檢索池**：73 條 concept（Phase 1.5 的 55 條 + 對照組 18 條）。
對照組也放進來是因為池子越小 recall 越虛高。

**ground truth 來自語料本身，不另外出題**：每條 concept 都記著自己來自哪兩輪，
那一輪的**使用者實際輸入**就是 query，正確答案就是該 concept。
共 62 個 query（過濾掉短於 20 字元的，「這個可以換下一個」本來就不該召回任何東西）。

刻意不用 `probe` 當 query——那是蒸餾階段為測該條記憶量身寫的，
拿它測檢索會得到漂亮但無意義的數字（`phase15-evaluation.md` 已經吃過這個虧）。

**embedding 走 ollama HTTP，不自己載模型**。這是關鍵決定：
`UserPromptSubmit` 只有 30 秒 timeout 且每次都是新程序，
自載模型等於每輪對話付一次冷啟動。ollama 是常駐服務，模型留在它的記憶體裡，
這邊只是一次 HTTP 往返——**也就不需要自己做 daemon**（原本規劃在 Phase 4）。
模型 `bge-m3`，與 PM（Open Notebook）一致，已知可行。

## 結果

| 設定 | recall@5 | recall@10 | MRR | 完全召不到 |
|---|---|---|---|---|
| BM25 | 35.5% | 45.2% | 0.256 | 15/62 |
| BM25 + scope | 50.0% | 59.7% | 0.314 | 15/62 |
| **BM25 + scope + cue** | **58.1%** | 66.1% | **0.436** | 10/62 |
| 向量 | 35.5% | 43.5% | 0.293 | 0/62 |
| 向量 + scope | 43.5% | 59.7% | 0.348 | 0/62 |
| 向量 + scope + cue | 53.2% | 67.7% | 0.380 | 0/62 |
| Hybrid(RRF) + scope | 54.8% | 67.7% | 0.362 | 0/62 |
| **Hybrid(RRF) + scope + cue** | **59.7%** | **69.4%** | 0.431 | 0/62 |

延遲：73 條建索引 2.0s、**單次查詢 371 ms**（含 HTTP 往返）。
對 30 秒預算綽綽有餘，BM25 單獨則是 0.32 秒含 Python 啟動。

## 主要發現

### 1. 提取線索的設計，比檢索演算法的選擇更重要

`cue` 在**每一種**檢索方式上都帶來提升，而且幅度比「BM25 換成向量」還大：

- BM25：recall@5 +8.1pp、MRR **+0.122**
- 向量：recall@5 +9.7pp、MRR +0.032
- 換向量（不加 cue）：recall@5 **±0.0pp**

原因是 asymmetric retrieval。`statement` 是**答案**的措辭，query 是**問題**的措辭：

> query：「建立者顯示的是 ID，我想看到操作者名稱」
> statement：「多租戶鐵律：反查 users 要一併帶 companyid 過濾」

語意上明確相關，但重心一個在「顯示名稱」、一個在「多租戶/companyid」，
BM25 與向量**雙雙落榜**。這不是演算法不夠好，是拿問題去比對答案本來就錯位。

這正是 Echo Memory 那個名字的意思——**Ecphory 是提取線索**。
記憶靠 cue 被喚起，不是靠內容本身被搜到。從 OpenSoul 繼承的設計意圖在這裡得到了實測支持。

### 2. 加了 cue 之後，零依賴方案幾乎追平混合方案

`BM25+scope+cue` 的 MRR（0.436）**略高於** `Hybrid+scope+cue`（0.431），
recall@5 只差 1.6pp。

工程含意：cue 寫得好的話，**可能根本不需要 ollama 依賴**——
純標準庫、0.32 秒、沒有外部服務相依。這對 hook 的健壯性是很大的差別
（ollama 沒開的話 hybrid 就退化，BM25 不會）。

建議的落地形態：**BM25 為主，ollama 可用時以 RRF 疊上向量**，
拿不到就自動退回純 BM25。兩者的差距小到足以當成 optional enhancement。

### 3. scope 過濾是免費的槓桿，但收益有一部分是機械性的

recall@5 +14.5pp（BM25）。不過候選池從 73 縮到 26，隨機基線也從 6.8% 升到 19.5%，
所以「提升倍數」其實是下降的（5.2x → 2.6x）。真實收益存在但不如表面漂亮。

無論如何這是免費的：hook 一定知道當前 repo，不用白不用。

## 天花板診斷：69.4% 其實已經接近極限

把 19 個未命中案例逐條判定「一個熟悉這個專案的人，看到這句 query 會不會想起這條筆記」：

| 判定 | 條數 | 意義 |
|---|---|---|
| `UNRETRIEVABLE` | **12（63%）** | 沒有可辨識的關聯，任何檢索都做不到 |
| `WEAK` | 3 | 間接關聯，人類也未必聯想得到 |
| `RETRIEVABLE` | 4 | 主題明確相關，檢索該抓到 |

換算：

```
62 個案例 − 12 個原則上不可能 = 真實天花板 50/62 = 80.6%
已命中 43 / 可召回 50 = 86.0%
```

**所以不是 69.4% 很差，是 86% 已經逼近極限。** 繼續優化檢索演算法最多再拿到
7 條（RETRIEVABLE 4 + WEAK 3），約 11pp，之後就撞牆。

### 那 63% 為什麼無解

1. **通用確認句污染**：query 是「可以 commit 了」「繼續處理」「同意，開始」，
   statement 卻是助手執行過程中順帶發現的技術細節。兩者在語意空間沒有連結。
2. **技能模板噪音**：部分 query 實際上是 jira-ticket-workflow 的技能說明全文
   加一句指示，真正的意圖被模板稀釋。**這一項可修**——建索引與查詢前剝離技能樣板。
3. **一問多果**：同一句寬泛的 query 對應多條不同的技術修復
   （「PageSpeed 報告後續處理」同時指向 AbortSignal 與 Astro hydration 兩條），
   單一 query 天然無法同時精準命中。

## 檔案訊號：另一條觸發路徑

第一種 ground truth 問的是「同樣的任務再來一次」。第二種問「**再次碰到這個檔案**時，
關於它的記憶會不會浮出來」——也就是 `PreToolUse` 的場景。

case 建法：對每條 concept，找出編輯了相同檔案、但**不是**它來源的 human 輪次。
共 251 個 case，涵蓋 46/73 條 concept。

| 訊號 | recall@5 | recall@10 | MRR |
|---|---|---|---|
| 文字（BM25+cue） | 27.5% | 41.0% | 0.181 |
| **檔案重疊** | **89.2%** | 100% | **0.560** |
| 檔案 + 文字（RRF） | 85.3% | 98.8% | 0.554 |

### 可信的發現：融合反而變差

加上文字訊號後 recall@5 從 89.2% **掉到** 85.3%。文字檢索在這個情境幾乎是隨機的
（27.5%），RRF 融進來就是往乾淨的排序裡摻雜訊。

**訊號要挑，不是全加。** 這推翻了「多訊號融合一定更好」的直覺，
而且這個比較是同一批 case、同一個 ground truth，公平可信。

### 要打折的部分：89.2% 這個數字本身

ground truth 是「編輯了同一個檔案的輪次」，檔案訊號就是「檔案重疊」——
**兩者共用同一個定義**，recall 高有機械成分，`recall@10 = 100%` 尤其是。

### precision 才是真相：30%

抽樣 30 個情境（去重自 251 個 case），共 63 條召回，由兩組獨立評審判定
「如果 agent 動手前看到這條，會不會做得更好」：

| 判定 | 條數 | 佔比 |
|---|---|---|
| `RELEVANT` | 19 | 30.2% |
| `MARGINAL`（同模組但沒交集） | 19 | 30.2% |
| `IRRELEVANT` | 25 | 39.7% |

```
每次觸發平均召回 2.13 條 → 其中約 0.64 條真正相關
```

召回量小是好事（不會塞爆 context），但**七成是雜訊**。

兩組評審**獨立得出同一個診斷**，所以這個結論可信：

> RELEVANT 案例的共同特徵是記憶命名的**檔案 / 函式 / 欄位跟本輪實際改動的對象同名同源**
> （z-index 數值、`assign_to` 欄位、`fogRatio` 欄位、`dispatchEchoPreview` 呼叫鏈），
> 而不只是「同一個檔案」。

雜訊的兩個來源：

1. **記憶掛在 repo / 大模組層級**，只要沾到同一個 repo 或相鄰目錄就被撈進來
2. **同一個檔案承載多個彼此無關的功能區塊**，抓到的是「同檔案裡另一段邏輯的舊筆記」

### 根因是我的設計缺陷，不是訊號本身的問題

`source_files` 存的是「產生這條記憶那一輪**碰過的所有檔案**」——那是**溯源**資訊，
裡面多半是順手碰到的。拿它當檢索錨點，等於用「當時剛好開著的檔案」去比對「現在要改的檔案」。

已修正：蒸餾階段新增 `anchors` 欄位，由 LLM 指出**這條記憶真正談論的具體對象**，
而且**粒度到函式名與欄位名**，不只是檔案路徑——那正是 RELEVANT 與 MARGINAL 的分界線。
`file_overlap_ranker` 優先用 `anchors`，沒有才退回 `source_files`。

**修正後的效果尚未實測**（舊語料沒有 anchors，要重跑蒸餾才有），這是下一輪的第一件事。

## 兩條路互補，不是二選一

天花板診斷的第 1 點與檔案訊號的結果接在一起，指向一個架構結論：

`UserPromptSubmit` 的檢索**天生受制於「使用者那句話有沒有主題訊號」**，
而真實對話裡有大量「繼續」「可以」「換下一個」（語料實測 human 輪次
user_text 中位數只有 58 字元）。檔案訊號完全不受這個限制——
不管使用者說什麼，agent 下一步要碰哪個檔案是確定的。

| 觸發點 | 管什麼 | 強項 | 弱項 |
|---|---|---|---|
| `UserPromptSubmit` | 使用者明確問到的主題 | 可召回案例達成率 86% | query 沒訊號就無解（天花板約 80%） |
| `PreToolUse` | 即將碰到的檔案 | 不受 query 品質影響，recall 高 | **precision 僅 30%**，錨點粒度太粗 |

兩者的失敗模式正好互補：文字訊號**漏掉**該召回的（query 沒主題），
檔案訊號**多召回**不該召回的（錨點太粗）。所以不該只選一個，
但也不能無腦融合——實測 RRF 把文字混進檔案訊號後 recall 反而下降。

## 已完成的修正（本輪）

1. ✅ **蒸餾階段正式產 `cue` 欄位**——「什麼情境下該想起這條」，用觸發情境的措辭而非答案的措辭。
   舊語料沒有此欄位時自動退回 `probe`。
2. ✅ **蒸餾階段新增 `anchors` 欄位**——這條記憶真正談論的對象，粒度到函式名與欄位名。
   `file_overlap_ranker` 優先用它。
3. ✅ **`statement` 要求原子化**——一條只講一件事，針對 42% 的 PARTIAL 灰帶。

以上三項都**尚未實測**：舊語料沒有新欄位，要重跑蒸餾才驗證得到。

## 待辦

1. **重跑蒸餾產生帶 cue / anchors 的語料**，然後重測 recall 與 precision。
   這是驗證上述三項修正的唯一方法，也是下一輪的第一件事。
2. **建索引與查詢前剝離技能樣板文字**——天花板診斷點出、明確可修的一項。
3. 檢索池目前只有 73 條，真實部署會到數百條，recall 會下降——現在的數字是樂觀估計。
4. **不要再往「換更好的檢索演算法」投資源**：可召回案例已達 86%，
   剩下的損失來自 query 本身沒有訊號，那要靠換觸發點與改進錨點解決，不是換演算法。

## 已知限制

- 檢索池 73 條偏小，recall 虛高
- 檔案情境的 ground truth 與檔案訊號共用定義，89.2% 有機械成分
- 檔案訊號的 precision 完全未測
- 每條 concept 只配一個 query；反過來「一個 query 對多條 concept」的情況
  已知存在（診斷成因 3），但未納入評測
- 未命中診斷由單一評審判定，無跨評審一致性數據
