# Phase 1.5：從語料蒸餾 concept + surprisal 行為校準（2026-08-07）

承接 `results.md`（記憶價值 = surprisal）與 `surprisal-calibration.md`（surprisal
只能靠行為測試測）。這一輪把兩者接成完整管線，跑在 Phase 1 累積的真實語料上。

## 管線

```
1372 輪語料
  → 結構訊號粗篩（同一檔案在相鄰 human 輪被再次修改）  → 78 組候選
  → LLM 蒸餾（6 個 subagent 並行）                    → 55 條 concept
  → 行為測試（9 個乾淨 subagent 作答，opus）
  → 判卷（4 個 subagent，看得到陳述與回答）            → 55 條全數校準
```

粗篩用結構訊號而非關鍵字，理由同 Echo 的架構禁令：用關鍵字清單決定什麼值得記住，
是對記憶形成的廉價模仿。這裡只看「做了什麼」——檔案被改了第二次，代表第一次沒改對。

受測 agent 用 opus 而非預設的 sonnet：記憶最終要影響的是主 loop 的行為，
拿別的模型測出來的先驗代表不了它。

## 結果

| 判定 | 條數 | 佔比 | 意義 |
|---|---|---|---|
| `CONTRARY` | 13 | 24% | 模型講了相反的話——**最高價值** |
| `SILENT` | 9 | 16% | 完全沒提到——有價值 |
| `PARTIAL` | 23 | 42% | 沾到邊但不完整 |
| `VOLUNTEER` | 10 | 18% | 模型主動講出來了——**注入純浪費** |

通過門檻（surprisal >= 0.8）：**22 條**。

行為測試確實在做事：18% 的蒸餾產物被判定為零價值。這些條目在蒸餾階段全都被
LLM 認為「模型不會知道」——再一次證明自評不可靠。

## 三個發現

### 1. 被淘汰的不是我預期的那批

蒸餾結果剛出來時，我一眼認定幾條通用 web 知識是雜訊，應該被殺掉：
`position: sticky` 建立堆疊上下文、`touchmove` 預設 passive、`scroll-snap-stop: always`。

行為測試的結果是——**一條都沒被殺掉**。而 VOLUNTEER 的 10 條裡有 9 條是
`project-fact`，正是我以為最安全的那一類。

其中 `scroll-snap-stop` 那條判定為 `SILENT`：模型在題目情境下完全沒想到這個屬性，
只把 proximity 手感異常歸咎於「瀏覽器判定寬鬆、snap point 太密」。它確實不知道。

**surprisal 與「通用還是專案特有」無關。** 通用知識裡有模型不知道的冷門角落，
專案特有事實裡有模型光憑命名慣例就猜得到的部分。只有實測分得出來，
而我的直覺在這件事上跟 LLM 自評一樣不可靠。

### 2. 複合陳述會讓判定失真 —— concept 必須原子化

`touchmove` 那條被判 `PARTIAL`，但看判卷理由：受測者**正確講出了**「預設 passive、
要 `{passive: false}` 才能 preventDefault」，被降級是因為沒提到陳述後半段的
Chrome scroll intervention。

也就是說這條 statement 綁了兩件事：一件模型知道，一件不知道。
行為測試只能給一個判定，於是得到一個既不能保留也不能剔除的中間值。

`PARTIAL` 佔 42% 是這個問題的規模指標——這麼高的比例不正常，
其中相當一部分應該是複合陳述被迫收斂到中間值，而不是模型真的「半懂」。

**修正方向**：蒸餾指示要求「一條 concept 只講一件事，能拆就拆」。
現有的 23 條 PARTIAL 值得逐條檢查能不能拆開重測。

### 3. 粗篩訊號有結構性盲區：抓不到立場分歧

55 條裡 `user-stance` 只有 1 條。

「同一檔案被改兩次」抓的是**技術陷阱**——模型寫錯了、被改回來。
但使用者的立場分歧（動工前先讀規格與附圖、逐項 commit 的定義、不要自作聰明）
往往**根本沒有檔案改動**，或者一次就對了。這條訊號按定義漏掉它們。

而 Phase 0 的黃金資料裡，`user-stance` 類的價值最高——它不是模型不知道的事實，
是模型會做出相反選擇的偏好。

補這塊需要另一種訊號，候選是「使用者輪次語氣強烈但沒有檔案改動」，
或「同一段話在不同 session 反覆出現」。尚未實作。

## 對 Phase 2 的修正

1. 蒸餾指示加上**原子性要求**，並回頭拆解現有的 23 條 PARTIAL 重測
2. 補 `user-stance` 的粗篩訊號，否則整套系統只會記得技術陷阱、記不住工作方式
3. 校準結果要綁模型版本——這批是 opus 測的，模型升級後 VOLUNTEER 的比例會上升，
   需要重跑（這正是 Dream Engine 在此情境的職責）
4. `scope=TestSeperateMemorySystem` 的 6 條有污染疑慮：受測 agent 在本 repo 目錄下
   執行，會自動吃到 CLAUDE.md。那 6 條的判定可信度低於其他條目

## 已知限制

- 受測 agent 一次答 6 題，題目彼此無關但仍可能互相影響作答風格
- 判卷只有單一評審，沒有跨評審一致性數據（`surprisal-calibration.md` 當時量到
  兩個自評者的一致性是 79%，判卷的一致性尚未量）
- 78 組候選只涵蓋 5 個 repo，其中 Eternity 佔 42 組，分布偏斜
