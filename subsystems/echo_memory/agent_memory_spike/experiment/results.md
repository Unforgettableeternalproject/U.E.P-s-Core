## 但真正的發現不在通過與否

有鑑別度與沒鑑別度的題目，分界線非常乾淨：

**有鑑別度（Q3 / Q5 / Q6 / Q7）**
- Q5：專案特有事實，而且**與 CLAUDE.md 的記載直接衝突**（CLAUDE.md 說「配置透過 config.py 管理」，
  B 組就照著答 config.py，完全沒提 `.env` 才是真正控制源）
- Q6：模型抱有**錯誤的預設信念**——B 組自信地說「ESM 模組同 session 只載入一次，
  兩個 island import 同一個檔案就會拿到同一個實例，天然達成共享」，並額外建議「避免用 window」。
  這與事實完全相反，而且它不會有任何疑慮
- Q7：**使用者的個人立場**與模型預設立場相反。模型預設「保留 fallback 比較安全」，
  艾斯維爾的原則是「權威鍵確立後啟發式全部退役」
- Q3：特定架構的非顯而易見後果（只 UPDATE 會讓遠端記錄復活）

**沒有鑑別度（Q1 / Q2 / Q4 / Q8）**
- 全部都是**通用最佳實踐**。模型訓練資料裡本來就有，注入它們純粹是浪費 context
- Q4 尤其明顯：B 組把 ngFor + getter 的變更偵測死結講得比黃金資料本身還詳細

## 結論：記憶的價值 = 模型不知道的程度，不是事情本身的重要程度

這推翻了規劃階段的假設。原本從 Echo Memory 繼承過來的想法是
「salience 衡量重要性，是權重不是門閥」——在對話記憶情境下這是對的，
但在 coding agent 情境下，**重要性與資訊增益是兩回事**。

「多租戶查詢要過濾 companyid」非常重要，但模型本來就知道，注入它的資訊增益是零。

**Q6 是最有價值的類型**：模型不只是不知道，而是**自信地相信錯誤的事**。
這類記憶價值最高——因為缺了它，agent 不會提問、不會查證，會直接做錯。

## 對後續階段的直接影響

1. **黃金資料有約一半是浪費**。39 條裡通用最佳實踐類（trackBy、後端驗證兜底、多租戶過濾、
   分散式鎖……）應該全部剔除
2. **Phase 2 的排序訊號要改**：不是 salience（重要性），而是 **surprisal（模型意外程度）**。
   自動萃取時需要一道「模型本來就知道嗎」的過濾
3. **跨專案共享的真正候選**收斂成兩類：
   - 使用者的個人立場 / 決策偏好（與模型預設立場相反的那些）
   - 模型錯誤預設信念的修正
4. **專案特有事實的價值放大**，特別是**與專案文件記載衝突**的那些（Q5 型）——
   CLAUDE.md 會主動把 agent 導向錯誤答案，這種情況下記憶是唯一的糾正管道
