# 決策模型（Laya）訓練設計草案

> 狀態：**草案，待艾斯維爾裁決**（2026-11-11，諾薇亞起草，敏卡派工）。
> 上游：[決策中樞架構提案](決策中樞架構提案.md) §3、§5、§9；[決策標註規格草案](決策標註規格草案.md)（v1，本文不改它，只補它沒覆蓋的 kind）；`uep/decision/*`。
> 範圍：只談**訓練資料與題目設計**；不改 `uep/` 下任何 production 程式。需要改 production 之處一律列在 §7 待裁。

## 0. 結論（先看這裡）

1. **決策中樞不是 turn.reply 的三題。** 現有 8 個 kind，其中只有 4 個的核心判斷是「讀一段自然語言」，適合 Laya；其餘 4 個的輸入是數值／狀態／版本號，判斷本質是門檻與授權，**留規則**，模型最多當輔助分數。
2. **分三批**：A 批（文字判斷，v1 就做）`turn.reply`、`presence.absent_intent`、`loop.consult(speak／ask_user)`；B 批（需多句窗口或迴圈事實，v1.5）`turn.interject`、`loop.consult(output_modality／followup／placement 的 executor 選擇)`、`proactive.initiate` 的軟性分數；C 批**不交模型**：`channel.mode`、`policy.snapshot`、`memory.dream`、`loop.consult(loop_end)` 目前也留規則（理由 §2）。
3. **資料只有一小塊能從 `train/nlp` 復用**：僅 `route`（CHAT／DIRECT_WORK／BACKGROUND_WORK → direct_chat／task_request／agent_loop）的種子；其餘全靠合成＋標註＋日誌。種子的文字偏模板（如把兩個不相干句子用逗號接起來），預設降權、只當 route 的輔助，不當主資料。
4. **訓練列要按 kind 擴充**：每個 kind 一份 `KindSpec`（題目、state 組裝、標註 schema、硬限制清單）。題目 ID 以 kind 為前綴；`turn.reply` 保留既有三題的舊 ID（`reply_mode`／`route`／`addressed`），不破壞現有 adapter。
5. **兩個會影響整個計畫的現況缺口**（§7 的 Q1、Q2）：現行 `QUESTIONS` 與 `build_state` 是**中文**，與「Laya 只吃英文」矛盾；Laya adapter 目前**拿不到前文**（`recent_context` 固定「無」），單字附和這類最關鍵的情境模型根本看不到。這兩點不解，微調出來的模型在上線時會與訓練分佈不一致。

## 1. 共通設計

### 1.1 模型的位置與輸出的處置

模型輸出只是 **Proposal／plan 片段的提議**（機率分佈），經 adapter 轉成既有 Proposal／advice，再走既有驗證（`validate_proposal`、consult 的 schema 與 CN-1 範圍交集）。**下列永遠是規則，不論模型多準**：

| 硬限制 | 位置 | 為什麼不交模型 |
|---|---|---|
| 全域停止、Presence 非 ACTIVE、audience 不允許 → 強制 `pass` | Core／Orchestrator | 安全閘，標註規格 §4 末列已排除 |
| Risky 核准、工具授權、`approval_level` | 工具註冊表／Approval | TG-2、PD-3：不看模型 hint |
| actor 認證、`is_owner`、grant／`authorization_ref` 查證 | Presence／proactive context | 提案 §18.3：意圖不是授權 |
| consult 的凍結集合 ∩ snapshot（CN-1）、跨平台 placement 與能力擴張 → escalate | `loop_consult` | Q26：擴權不可由模型決定 |
| Lease、dream 預算與退避、冷卻 ledger、每日預算 | `DreamPlanner`／`arbitrate` | 狀態性資源控制，不是語意判斷 |
| 逾時／busy／例外／輸出驗證失敗 → fallback（D80 預設、`FAILSAFE_DEFAULTS`） | 各 engine | 模型永遠可被放棄 |
| 信心不足時的降級（低於門檻改走規則或 `pass`／`ask`） | adapter | 閾值由 `calibrate` 在 val 上決定，不進訓練 |

做法：**模型只看「它被允許選的選項」**（例如 placement 只列 `available_executors`，不列跨平台選項），輸出之後仍再過一次規則過濾。

### 1.2 輸入語言與 state

- 所有**使用者來源的自然語言**（`message`、前文）先經 MT 成英文再進 state；ID／列舉／數值本來就是英文，不經 MT。「給 LLM 的原文不變」不受影響。
- 訓練時的 state 必須與推論時的 state **逐字同形**（同一個 builder）。因此 builder 只在 `train/decision/laya_data/kinds.py` 定義一份，推論端（`laya_wiring.build_state` 及各 kind 的 adapter）日後應改為共用或以測試鎖定相等（見 Q1）。
- 推論輸入實際是 opus-mt-zh-en 的譯文，且助理別名會被換成佔位名（`UEP_TRANSLATE_PLACEHOLDER`，預設 `Yuki`）：state 的 `assistant_name` 與合成文字稱呼助理時一律用 `Yuki`。訓練語料要含「**MT 譯文腔**」與「STT 噪音」的變體，因為實際輸入是 zh→en 機翻。測試集必須由 zh-TW 原句經同一條 MT 產生、人工核過，絕不從英文原生樣本取。

### 1.3 laya-train 格式（已在 0.4.22 原始碼確認）

每列 JSON：`{"state", "questions", "expected"}`，`gold` 可取代 `expected`（`gold[qid].probabilities` 給軟標籤）。

- `state`：字串或 dict（dict 以 `json.dumps(ensure_ascii=False)` 序列化，所以**鍵順序也屬於分佈**，builder 必須固定順序）。
- `questions[qid]`：`{"type": "choice"|"noul"|"score", "instructions", "criteria"}`；choice 的 criteria 是 `label → 說明` 的 dict 或 label list；score 的 criteria 是層級說明 list；noul 無 criteria。
- `expected[qid]`：choice 為 label 字串；noul 為 bool；score 為層級索引或字串。只列有標註的題，**沒列的題不計入、不算負樣本**（這讓同一列只標部分題成為可能，也是 train/nlp 種子只標 `route` 的依據）。
- 同一 `qid` 在不同列的定義不同只會警告並保留第一個 → **qid 必須在全資料集內定義唯一**，故跨 kind 同名題一律加前綴。
- 額外鍵（`kind`、`sample_id`、`source`…）被忽略，可安全放 metadata；但**標註規格要求標註檔不含原文**，所以 metadata 只放 ID／列舉，原文只在 `state`（訓練列本來就是內容池的衍生品，不入標註檔）。
- 共用 venv 未裝 laya；確認動作在 scratchpad 的臨時 venv 完成，未動共用 venv。

### 1.4 資料來源分層與標籤可信度

| 層 | 內容 | 標籤來源 | 可信度與用途 |
|---|---|---|---|
| S1 `train/nlp` 種子 | 英文、約 6300 筆 | 舊 NLP 標註 → 對映表 | 低到中；只用於 `route`；選用 |
| S2 情境卡合成 | 依卡片生成文字 | **標籤由卡片決定（確定性）**，LLM 只生文字 | 中；量大；**會把我們的判準複製進模型**（自我實現），所以不可當評估依據 |
| S3 手寫／艾斯維爾本人日誌（`real_owner`） | 私有池，不入 git | 人工標註（規格 §5 雙標） | 高；量小；dev／test 的唯一來源 |
| S4 zh-TW 原句經 MT | 測試集 | 人工核＋雙標 | 最高；凍結後只開一次 |

規則：**train 可含 S1+S2+S3；val 取自 S2/S3 的獨立情境；test 只用 S4**，並以腳本檢查與 train 無字面／近似重疊。S2 合成標籤與「規則版輸出」不得互相引用（延續規格 §1）。

## 2. 決策 kind 盤點

欄位說明：**輸入 facts** 為英文化後送模型的內容；**輸出／plan**為該 kind 現有的 outcome 與 plan 區段；**題目**為建議給 Laya 的題型。

### 2.1 `turn.reply`（sync，300ms，A 批）

- 輸入 facts（英文化）：`assistant_name`、`speaker`（泛稱 `User`／`S1`）、`other_people_present`（`none`／`N others present`）、`recent_context`（前 ≤6 句，附 `age`；**現況缺，見 Q2**）、`message`（MT 後全文）。選填給輔助特徵：距上次回覆秒數、是否剛被打斷（規格 §2.1 情境卡；用文字化的列舉，不用原始數值）。
- 輸出／plan：outcome＝`reply_mode`（respond／passive／pass／defer）；`plan.route`（direct_chat／agent_loop／task_request／ignore）；`plan.reply.addressed`、`interaction_to`；`plan.capability.capability_hint`（只收窄）。
- 題目：`reply_mode` choice(4)、`route` choice(4)、`addressed` noul（沿用現有三題 ID）；規格 §3.2 的 `risky` choice(3) 與選填 `content_risk` 作為**輔助題**，另設 ID `risky`／`content_risk`，只在有標註時才列入 expected。
- 留給規則：硬閘（§1.1）、`interaction_to`（由 speaker_ref 查表，不由模型）、`capability_hint` 的最終標籤、Risky 核准、barge-in 冷卻（規格 §4 已說冷卻是政策）。模型不學冷卻。
- 資料：S1 提供 `route`（`ignore` 在 S1 完全沒有，只能靠合成）；S2 依情境卡（§4）生成 reply_mode／addressed／route；S3 提供真實分佈與難例。

### 2.2 `turn.interject`（async，A 批之後，B 批）

- 輸入 facts：**一批 buffer 對話**（多句、說話者代號 `S1..Sn`、各句 `age_s`），加情境卡（人數、距上次 UEP 發言秒數）；沒有「新輸入」。
- 輸出：outcome 只取 respond／pass（規格 §2）；plan 只有 `reply`。
- 題目：`interject.reply_mode` choice(2)；`interject.value` score(0..3，插話價值——比二元更能用閾值調敏感度，閾值屬 calibrate 而非訓練)。
- 留給規則：被動模式才可插話、冷卻、inflight、barge-in cooldown、context_confidence 衰減。「插話代價高於漏插」→ 預設 `pass`，模型輸出須超過保守閾值才採用。
- 資料：需要多句窗口，S1 無法復用；S2 合成多人對話窗口（有「無人答的問題」「提到 UEP 先前承諾」「純人際閒聊」三類）；S3 需要艾斯維爾日誌的窗口。這是標註難度最高的 kind，**v1 不做**，先收窗口樣本。

### 2.3 `presence.absent_intent`（sync，300ms，A 批，優先）

- 輸入 facts：`message`（MT 後）、`source_platform`（列舉）。**不放** `actor_ref`／`is_owner`／`actor_authenticated`：它們雖允許當特徵，但放進訓練會讓模型把「是不是 owner」學成意圖線索，與「只產生意圖、不產生授權」相悖；授權永遠由規則在模型之外判斷。
- 輸出／plan：outcome＝`presence_request`／`message`／`other`；選填 `target_location`（desktop／discord／website／host）；`plan.placement` 僅記錄意圖。
- 題目：`absent.intent` choice(3)、`absent.target_location` choice(5，含 `none`；只在 intent＝presence_request 的列才列入 expected)。
- 留給規則：授權、優先序、是否受理移轉、Presence 狀態機；低信心（<門檻）回 `other`（保守，規格 §8.2）。
- 資料：標註規格 §8 已給正反例。S1 不覆蓋；S2 以「肯定請求／否定／過去敘述／疑問能力／提到場域名稱／傳話」六類加 target 組合生成，是**最適合先做合成**的 kind（類別定義清楚、文字短）。S3 不需要日誌。

### 2.4 `loop.consult`（sync，300ms；6 個 sub_kind）

共通 facts：`sub_kind`、`ordinal`、`frozen`／`capability_snapshot`（**範圍由規則算，不送模型**；模型只收到交集後的合法選項）。

| sub_kind | 輸入 facts（英文化） | 輸出 advice | 建議題目 | 留規則 | 批次 |
|---|---|---|---|---|---|
| `speak` | `user_present`、`result_ready`、迴圈摘要（一句英文，描述目前進度；**現況缺**） | `reply.mode`（respond／passive／pass／defer） | `consult_speak.reply_mode` choice(4) | failsafe＝`hold`；範圍檢查 | A（需 Q3） |
| `ask_user` | `confident_default`、待決問題摘要 | `reply.mode`∈{defer, ask} | `consult_ask.mode` choice(2) | failsafe＝`ask` | A（需 Q3） |
| `output_modality` | `proposed_modalities`、輸出內容類型（短答／長文／提醒…的列舉）、使用者是否在場 | modalities、tts、history、emotion | 每個 modality 一個 noul＋`tts` noul＋`history` choice(2) | modalities 必須 ⊆ frozen∩snapshot；emotion 只能是 preset | B |
| `placement` | `current_platform`、`available_executors`、任務類型列舉 | 同平台內換 executor | `placement.executor` choice（選項＝`available_executors`，隨列變動） | **跨平台、request_move、audience_scope_max 一律 escalate**，不進模型 | B（價值低，可能永遠規則） |
| `loop_end` | `goal_satisfied`、`made_progress`、`consults_used`、`no_progress_count` | continue／finalize | — | 輸入全為布林／計數，規則已是決定性；上限（MAX_CONSULTS／NO_PROGRESS_N）是預算 | **不做** |
| `followup` | `report_pending` | completion_report 或無 | `followup.report` noul | failsafe＝none | B |

- 重點：consult 的 facts 目前**沒有任何自然語言**（`result_ready` 這類旗標），模型學不到比規則多的東西。要讓 Laya 有價值，必須加入「迴圈摘要／使用者最新訊息」之類英文字串欄位，這是 production 的 facts schema 變更（Q3）。沒有它，A 批的 consult 只是用旗標湊的玩具資料，**不建議先做**。
- 資料：全部合成（旗標組合＋摘要句）；沒有 S1；S3 需要 Agent Loop 的真實 run 摘要（日誌尚未存在）。

### 2.5 `proactive.initiate`（async，shadow-only，B 批）

- 輸入 facts：`candidate`（goal_ref、urgency、confidence、memory_salience、privacy_scope、source_kind、距到期時間…，皆為 ID／列舉／數值）與 `context`（presence、activity_cost、cooldown ledger、預算…）。
- 輸出：outcome＝ready／deferred／rejected；plan 的 loop／placement／followups。
- 9 關裡**硬關（validity、stop、authorization、audience、presence、duplicate、cooldown、budget）全留規則**，且「高分不得抵銷」。可交模型的只有軟關：`cost`（打擾成本 vs. 價值）與 `confidence`。
- 題目：只做 `proactive.worth` score(0..4)：「現在提醒這件事值得打擾使用者嗎」，輸出當成**第 6 關的輸入特徵**，不能覆蓋硬關。
- 資料：沒有任何文字，facts 是結構化欄位；合成標籤只會複製目前的 `_URGENCY_WEIGHT`／cost 公式。**需要艾斯維爾對「這個時機該不該提醒」的真實偏好**（S3 才有意義），v1 不做。

### 2.6 `memory.dream`（async，30s tick，C 批：不做）

- 輸入：`DreamSnapshot`（quiet_for_s、pending、daily_cycles、rest 窗、last_trigger、lease…），全為數值；輸出 run／wait＋trigger 類別（host_daydream／idle／backlog／rest）。
- 判斷幾乎全是門檻、預算、Lease、退避，屬「資源控制」；模型沒有語意可學。**合成資料只會把 `DreamLoopConfig` 的門檻複製一次。** 結論：留規則；等 `decision_log` 累積後，若要調門檻，用日誌做**離線參數校準**，不用 Laya。

### 2.7 `channel.mode` 與 `policy.snapshot`（publish，C 批：不做）

- 兩者 engine 只是**記錄器**：驗證 facts 型別後原樣記錄，不重新計算（版本連號、同版、模式一致是不變量審計）。真正的 active／passive 翻轉在 rule proposer 的 `ModeController`（人數、耦合度、遲滯，時間序列數值）。
- 結論：`policy.snapshot` 是純不變量，永遠規則。`channel.mode` 的翻轉依賴時間序列與遲滯，不是文字判斷；留規則，日誌累積後可離線調參。

### 2.8 彙整

| kind | 模型價值 | 批次 | 題目數 | 主要資料 |
|---|---|---|---|---|
| turn.reply | 高 | A | 3＋2 輔助 | S2 為主、S1 補 route、S3 驗證 |
| presence.absent_intent | 高 | A | 2 | S2 |
| loop.consult speak／ask_user | 中（需 facts 加文字） | A 或 B | 2 | S2 |
| turn.interject | 中 | B | 2 | S2＋S3 |
| loop.consult output_modality／followup／placement | 低到中 | B | 數題 | S2 |
| proactive.initiate | 低（只有軟關） | B | 1 | S3 |
| memory.dream、channel.mode、policy.snapshot、loop_end | 無 | C | 0 | — |

## 3. 管線架構（每 kind 一份 KindSpec）

```
train/decision/
├── README.md
├── laya_data/
│   ├── kinds.py        # KindSpec 註冊表：questions、state builder、expected 驗證、硬限制清單（文件用）
│   ├── convert_nlp.py  # S1：train/nlp → laya-train JSONL（只 route），含對映表與統計
│   ├── synth.py        # S2：情境卡矩陣 → prompt → 後端 → 驗證／去重 → JSONL
│   └── split.py        # train/val 切分；與測試集的重疊檢查
├── testset/            # S4 的 zh-TW 原句草稿（待人工核）
├── pool/               # synthetic 內容池（入庫，由 synth 產生，量產後才有）
├── pool_private/       # real_owner（.gitignore）
└── out/                # laya-train 輸出（.gitignore）
```

- `KindSpec` 欄位：`kind`、`questions`（含 qid 前綴規則）、`build_state(facts)`、`validate_expected(expected)`、`scenario_cards`（合成用）、`hard_rules`（說明用字串）。新增 kind＝新增一份 spec 與其情境卡，轉換器／切分／去重共用。
- 目前實作 `turn.reply` 與 `presence.absent_intent` 兩份；其餘 kind 先只在本文件，等 Q3 等裁決後再加。
- `synth` 的原則：**標籤由情境卡決定，LLM 只生文字**；不讓 LLM 自己給標籤（避免標籤噪音與費用）。難例卡（`hard=true`）在輸出與統計中單獨標記。
- 費用控制：每次執行有硬上限（試產 ≤200 筆）；沒有 `--confirm-api` 旗標不會呼叫外部服務；金鑰只從環境變數讀取，不寫檔、不印出。

## 4. 情境卡（turn.reply 的合成矩陣）

標籤依標註規格 §4。`R/P/D/S` 代表 respond／pass／defer／passive。

| 卡 | 設定 | reply_mode | addressed | route | 難例 |
|---|---|---|---|---|---|
| private_chat | 單人，聊天陳述 | R | 是 | direct_chat | |
| private_question | 單人，提問 | R | 是 | direct_chat | |
| private_task | 單人，單一明確指令 | R | 是 | task_request | |
| private_complex | 單人，多步規劃 | R | 是 | agent_loop | |

多樣化維度（對每張卡獨立抽樣）：風格 `clean`／`casual`／`stt_noise`／`mt_style`；話題領域；句長；說話者人數。去重：正規化（小寫、去標點、空白）後精確去重，另以 token Jaccard ≥0.85 視為近似重複，保留第一筆。

`presence.absent_intent` 的卡：六類（肯定請求／否定／過去敘述／疑問能力／僅提到場域名／傳話）× target 組合，標籤依規格 §8。

## 5. 切分與測試集防洩漏

- 切分單位是**情境卡內的 group**（同一張卡同一輪生成的樣本視為同組，規格 §5「同一對話不可跨集」）；以 `sha1(group_id)` 決定 train／val，可重現。
- 測試集（S4）= `testset/` 的 zh-TW 原句 → 經與生產相同的 MT → 人工核英文 → 雙標。**訓練工具永遠不讀 `testset/`**；`split.py check` 在 train 與 test 英文文字之間做正規化精確比對＋Jaccard 近似比對，任何重疊即非零退出碼。
- 目前只建「zh-TW 原句草稿」約 60 句（`testset/zh_candidates_draft.jsonl`，每列 `status=pending_review`），涵蓋 reply_mode 各類與 presence 意圖，**待艾斯維爾逐句核**（刪改後才能進 MT）。草稿內的「預期標籤」只是出題意圖，不是真值；真值以雙標為準。

## 6. 隱私與授權

- 不收他人資料；`real_owner` 日誌只進 `pool_private/`（已列 `.gitignore`），`speaker_ref` 換成 `S1..Sn`。
- 合成資料由外部 LLM 後端產生：prompt 不含任何真實日誌或個資；金鑰不入檔。
- `train/nlp` 資料沿用 repo 現況（專案自有資料），轉換產物若含其文字，屬衍生資料，放 `out/`（ignore）。
- 外部 LLM 產生的合成文字之使用條款：以所用服務條款為準，**上線前請艾斯維爾確認**（不影響本草案設計）。
